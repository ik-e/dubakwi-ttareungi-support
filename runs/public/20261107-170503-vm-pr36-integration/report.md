## 정상 한 건과 전체 회귀의 구분

Discord의 등록 사용자 질문 → 사용자 확인 → 분류 → 실제 검색 → 답변 작성·검증 → Jira 종료·Resolution → state의 최종 save/finish → 비공개 응답을 실제로 확인했다. 사용자는 QR 문의 답변과 두 개의 rental-guide 근거를 받았고 **본인만 볼 수 있음**을 확인했다. 독립 Jira·DB 재조회가 일치하고 DLQ는 0건이다.

최종 시험 사본 비활성화·n8n 재시작·44청크 재색인 이후에도 새 정상 요청이 자동 답변으로 끝났다. HTTP 11.988초, Jira 종료·Resolution, DB completed, 응답과 저장된 업무 필드 일치, DLQ 0건을 확인했다. 직접 정상 요청의 다른 표본은 14.817초와 9.934초다. 이 수치는 일반 목표 8초 충족이나 모든 요청의 성능 보장을 뜻하지 않는다.

## 그대로 남긴 실패와 한계

1. **WF11:** 실제 조회 timeout 뒤 안전 이관했지만 8.288초로 원 사례의 6초를 넘었다. 설계 7.5의 20초 시한/25초 관측 상한과 6초 가이드 예시의 범위가 다르다. 기대값을 바꿔 통과시키지 않았으며 6초 미충족으로 남긴다.
2. **TC15:** 첫 알림 결과 미확인은 partial_effect로 맞았으나 같은 문의 후속은 원 사례의 200/partial_effect 대신 현행 저장 설계에 따라 409 case_busy였다. 원 기대와 실패를 보존한다. unknown 후속 차단과 alert_marker 모듈 중복 제거를 서로 다른 시험으로 정리할 최종 R05 확인이 필요하다.
3. TC06의 종료 실패 추가 변형 한 번은 입력이 보완 질문으로 분류돼 종료 단계에 도달하지 못했다. 해당 실패를 보존하고, 종료 실패 자체는 QR 입력의 TC18에서 실제 Jira 거절로 검증했다.
4. TC07 자동 재처리 드라이버는 미구현이다. DLQ resolve나 state.fail은 원 요청의 재개가 아니다.
5. 담당/운영 알림은 과정 알림 API 수락까지 확인했다. 수락은 사람의 수신·인수를 뜻하지 않는다. 장애 기록에서 운영 알림 수락 10건, 알림 응답 유실 사례에서 실제 알림 호출 1회를 확인했다.
6. 자연어의 모든 표현, 최초 설계의 반복 횟수 전체, 외부 401/403/429의 실제 서비스 장애, Discord 전송 실패·긴 답변의 실제 서버 고장 주입을 모두 실행한 것은 아니다. 로컬 통제 시험과 실제 연결 결과를 합쳐 전부 실연동 PASS로 세지 않는다.

## 권한·시간·보안·복원

- AUTH01~07은 실제 n8n의 API → B05 → B13 → 실제 RAG 구간에서 7/7 기대를 확인했다. AUTH01/02/04/06은 실제 사용자 API 출력이다. AUTH03/05/07은 public 전용 담당자·503·과정 호환 형식의 통제된 API 출력 fixture다. 시민은 public만, 제한 권한 담당자는 restricted 근거까지 받았고, 미등록/503은 검색을 호출하지 않았다. 전체 support/Jira 7건으로 확대하지 않는다.
- 실제 B17 표본 9개 중 1개가 작성 3.512초·검증 2.634초로 줄어든 예산에서 write 경로를 실행했다. 일반 시한 20초와 최종 관측 상한 25초를 변경하지 않았다.
- 재전송/후속 차단 3건은 LLM·RAG·Jira·state.fail·DLQ를 다시 호출하지 않았다. 알림 재전송이나 자동 재개는 하지 않았다.
- 팀 키·내부 키를 교체했고 네이티브 인증을 유지한 채 저장 전 헤더 가림을 적용했다. 새로 저장된 실행 357개의 현재 팀/내부/Jira API·Basic/DB/OpenAI/봇 비밀값 대조는 모두 0건이었다. 과거 원문·백업에 남은 폐기 키와 새 키의 비저장을 구분한다. 과거 실행 원문을 삭제한 것으로 기록하지 않는다.
- PostgreSQL 백업을 별도 DB에 실제 복원해 기존 request 142행·DLQ 11행과 전체 행 집계 일치를 확인했다. 모든 시험 후에도 기존 scope의 행 집계가 원 복원본과 같다.
- n8n은 네트워크 none·공개 포트 0의 별도 복원 볼륨에서 SQLite integrity, Credential 6개 복호화, workflow 60개와 암호화 행/버전 일치를 확인했다. 복원 도구 실행은 32.062초였으며 운영 전체 RTO/RPO로 주장하지 않는다. 복원본의 폐기 키는 활성화 전에 현행 키로 바꿔야 한다.
- 시험/진단 사본 30개는 삭제하지 않고 비활성화했다. 정상 state/DLQ/errors는 n8n 2.42.6의 Execute Workflow 호출을 위해 게시 버전을 유지한다. 외부 Webhook이 없는 하위 흐름의 게시와 공용 Webhook 공개를 구분한다.
- 최종 키 소비처 검사: 팀/내부 새 키는 인증 뒤 잘못된 입력에400, 구키·누락·오키는401이다. 사용자 API의 구 내부 키도401이다. Discord의 서로 다른 5개 사용자 매핑은 모두 등록 시민/public으로 조회됐고 새/기존 파일 소비처4개의 값 일치와0600을 확인했다. 첫 검사 도구는401의 텍스트 본문을 JSON으로 읽다가 중단됐으며 파싱만 수정해 재검증했다.

최종 배포 대조는 컨테이너4개의 실행 이미지 ID와 업무 흐름7개의 게시본·연결·설정 일치를 확인했다. 원본에 없던 노드 UUID만 n8n 생성 메타데이터로 구분했으며 업무 코드/매개변수는 제외하지 않았다. 기존 흐름60개는 노드·연결·설정·게시 버전이 그대로이고 시험 사본30개는 비활성이다. 봇 Gateway 재연결과 비밀값 없는 VM 비공개 인계를 확인하고 임시 진행 모니터를 종료했다.
