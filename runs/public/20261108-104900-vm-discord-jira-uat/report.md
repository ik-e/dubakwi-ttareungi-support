# Discord·Jira 시나리오 UAT 결과

- Run ID: `20261108-104900-vm-discord-jira-uat` (KST 기준; UI 관측 10:43~10:49)
- 환경: Edge 웹, PR36 연결 Discord 시험 채널 및 두바퀴 Jira 프로젝트
- 기준: [시나리오 시험 안내서](../../../cases/discord-jira-user-acceptance.md)
- 배포/워크플로우 버전: UI에서 정확한 게시 버전·커밋을 확인하지 못함
- 계정/문의 문장/`case_ref`/실제 issue key는 공개 기록에서 제외

## 요약

등록된 Discord 계정의 비공개 문의 응답, 담당자 이관, 같은 문의의 Jira 티켓 재사용, Jira 상태 전환, 종료 뒤 소유자 상태 조회를 실제 UI에서 확인했다. 이 증거는 안내서 전체 시나리오 통과를 뜻하지 않는다. 실제 담당자 열람/Discord 수신, 출처 렌더링, 접근 경계, DLQ UI, 장애 주입은 이 실행에서 검증하지 않았다.

## 실행 중 별도 관측

입력 조작 중 선택 필드를 펼치기 전에 Enter를 눌러 `case_ref` 없는 별도 synthetic 문의 한 건이 추가 접수됐다. 이 건은 별도 문의로 처리되어 반납 안내와 별도 연결값을 반환했고, Jira key는 응답에 없었다. 테스트 데이터이지만 저장된 request/case 상태는 이 화면만으로 확인할 수 없어 0건이라고 주장하지 않는다. 이 건을 본 시나리오 통과 증거에 합산하지 않았다.

## 효과 및 한계

- Jira: synthetic 이슈 1건을 생성·상태 변경했으며, 시험 메모에 실제 이용자 조치가 없음을 표시했다.
- Discord: 테스트 채널에서 slash command를 제출했고 봇의 비공개 응답을 확인했다.
- DB/n8n 실행 로그의 저장 상태·외부 호출 횟수는 이번 브라우저 관측에서 검증하지 않았다.
- 상태 조회는 Jira 완료 상태와 일치하는 종료 안내를 돌려줬다. 화면 표현만으로 내부 상태 코드나 DB 원자성을 추정하지 않는다.
- Jira의 알림 표식은 실제 담당자의 Discord 수신·열람을 증명하지 않는다.
- DLQ 운영자 조회는 별도 [TC-07 VM 읽기 전용 결과](../20261108-101605-vm-tc07-dlq-lookup/report.md)를 참조한다. Jira 화면에서 DLQ를 관리하는 기능은 안내서대로 미지원이다.

## 총 판정

**핵심 이용자→Jira→완료 후 이용자 조회 흐름은 실연동으로 확인. 안내서 기준 전체 UAT는 미완료.** 실행 가능한 나머지 시나리오와 격리된 고장 시험은 각각 실행 증거가 필요하다.
