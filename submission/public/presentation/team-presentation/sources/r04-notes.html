R04 역할 담당자 담당 기능 구조와 구현 개념

1. 담당 역할

두바퀴 프로젝트에서 R04 역할 담당자는 사용자 문의가 실제 업무로 안전하게 이어지도록 외부 서비스와 저장 기능을 연결하는 역할을 담당했다.

AI가 만든 답변을 Jira 티켓으로 연결하고, 처리 상태를 저장하며, 같은 요청이 중복 처리되거나 실패한 작업이 사라지지 않도록 관리하는 부분이다.

주요 담당 기능

  • Discord 문의 입구와 결과 전달
  • 사용자 권한·문의 소유권 확인
  • Jira 티켓 조회·생성·보완·종료·배정
  • State 저장과 중복 요청 방지
  • DLQ와 오류·복구 처리

    • 2. R04 담당 기능 독립 구조도

    다른 팀원의 AI 분류·RAG 기능을 제외하고 R04 담당 기능만 분리하면 다음과 같다.

    flowchart LR
    U[Discord 사용자] --> D[Discord 어댑터]

    N --> A[사용자·소유권 확인]

    N --> H[Jira Handoff]

    A --> API[사용자 API]

    R04는 단순히 서비스를 연결하는 것이 아니라, Jira 변경 전후의 상태를 확인하여 중복 티켓·잘못된 재처리·결과 유실을 막는 역할을 한다.

    5. 기능별 실제 처리 흐름

    5.1 Discord 문의 전달

    /문의 슬래시 명령
    ↓
허용 서버·채널 확인
    ↓
Discord 사용자 ID와 문의 내용 변환
    ↓
n8n Webhook 호출
    ↓
가린 결과를 비공개로 전달

    Discord ID만으로 권한을 부여하지 않는다. 사용자 API가 등록 사용자와 역할을 다시 확인한다.

    5.2 사용자 권한·소유권 확인

    사용자 조회
    ├─ citizen → public
    ├─ support/security → public + restricted
    └─ 미등록·조회 장애 → 처리 중단

    문서 검색 권한과 Jira 문의 소유권은 별도로 확인한다. public 문서를 볼 수 있어도 다른 사용자의 문의를 조회할 수는 없다.

    5.3 Jira 티켓 처리

    flowchart TD
    T[처리 요청] --> P[State prepare]
    P -->|성공| L[Jira 기존 티켓 조회]
    P -->|실패| STOP[외부 변경 중단]
    L -->|기존 티켓| REUSE[연결 확인 후 재사용]
    L -->|없음| CREATE[신규 티켓 생성]
    CREATE --> B[생성 ID State bind]
    B --> C[문맥·보완 횟수 저장]
    C --> A{처리 종류}
    A --> CLOSE[종료]
    A --> ASSIGN[담당 배정·알림]
    A --> WAIT[보완 대기]

    Jira 변경 전에 prepare, 생성 직후 bind, 최종 결과 후 finish를 확인한다. 저장에 실패하면 다음 외부 변경을 중단한다.

    5.4 State와 중복 방지

    State에는 요청 ID, 소유자, 처리 단계, 확인된 Jira ID 등 안전한 처리에 필요한 최소 정보만 저장한다. 완전 재전송은 Jira 작업을 반복하지 않고, 새 보완 문의는 기존 티켓에 새 문맥과 횟수만 추가한다.

    5.5 DLQ와 오류 복구

    작업 실패 또는 결과 미확인
    ↓
확인된 Jira ID와 처리 효과 보존
    ↓
Recovery Capsule 생성
    ↓
DLQ 저장
    ↓
실제 상태 확인 후 필요한 단계만 복구

    결과는 성공·실패·결과 미확인으로 구분한다. 결과를 확인하지 못한 작업은 바로 반복하지 않고 DLQ에 보관한 뒤 실제 상태를 먼저 확인한다.

    8. 발표할 때 사용할 설명

    30초 설명

    저는 두바퀴 프로젝트에서 연동과 안정성을 담당했습니다. Discord로 들어온 문의를 n8n에 전달하고, 처리 결과를 Jira 티켓으로 생성·조회·종료하는 흐름을 연결했습니다. 또한 같은 요청으로 티켓이 중복 생성되지 않도록 State를 관리하고, 실패하거나 결과를 확인할 수 없는 작업은 DLQ에 보관하도록 구성했습니다. 즉, AI의 답변이 실제 민원 업무로 안전하게 이어지도록 만드는 역할입니다.

    1분 설명

    제 담당은 R04 연동·안정성입니다. 사용자 입구인 Discord, 자동화 도구인 n8n, 업무 관리 도구인 Jira, 상태 저장용 PostgreSQL을 연결했습니다. 이 과정에서 가장 중요하게 본 것은 단순 연결이 아니라 외부 작업을 안전하게 관리하는 것이었습니다.

    Jira 티켓을 만들기 전에는 처리 의도를 저장하고, 생성 직후에는 Jira ID를 기록하며, 마지막에는 처리 결과가 저장됐는지 확인하도록 했습니다. 같은 요청이 다시 들어오면 기존 티켓을 재사용하고, 새로운 보완 내용만 저장하여 배정과 알림이 반복되지 않게 했습니다. 실패하거나 성공 여부를 알 수 없는 작업은 바로 다시 실행하지 않고 DLQ에 남겨 실제 상태를 확인할 수 있도록 했습니다.

    9. 소감

    처음에는 API 연동이 한 서비스의 데이터를 다른 서비스로 전달하는 작업이라고 생각했다. 하지만 실제로 구현해 보니 요청이 중간에서 실패하거나, 작업은 성공했지만 응답을 받지 못하거나, 같은 요청이 다시 들어오는 상황까지 생각해야 했다.

    특히 n8n을 통해 Discord와 Jira를 연결하고, Jira 티켓이 생성되기 전후의 상태를 직접 다뤄 본 경험이 기억에 남는다. 다른 팀원이 구현한 분류·검색·답변 기능과 내가 담당한 Jira·저장 기능을 하나의 흐름으로 연결하면서, 팀 프로젝트에서는 각 기능 자체뿐 아니라 서로 주고받는 데이터 형식과 오류 처리 기준도 중요하다는 것을 알게 됐다.

    이번 프로젝트를 통해 AI가 답변을 만드는 과정만큼 그 답변을 실제 서비스와 안전하게 연결하는 과정도 중요하다는 것을 배웠다. R04 기능은 사용자 화면에서 직접 보이는 부분은 적지만, 중복 접수·결과 유실·권한 문제를 막기 위해 꼭 필요한 기반이라고 생각한다.
