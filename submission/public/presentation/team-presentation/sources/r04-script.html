R04 역할 담당자 발표문 (슬라이드 3장)

슬라이드 번호는 r04-3slides.html과 같습니다. 대괄호 [ ]는 발표 직전에 결과를 보고 채우는 부분입니다. 전체 3~4분 기준입니다.

슬라이드 1. 담당 역할

R04를 맡은 역할 담당자입니다. 문의가 R02 본체를 지나고 나면, 그 뒤의 기록과 Jira, 실패 처리, 그리고 Discord 입구가 제 담당입니다.

구조도를 보시면, 왼쪽의 Discord에서 /문의가 들어오면 제 어댑터가 받아서 R02 본체로 넘깁니다. R02가 접수 대장, Jira 담당, 사용자 API를 부르고, 상태와 실패 기록은 PostgreSQL에, 티켓은 Jira에 쌓입니다. 점선은 실패했을 때 가는 길입니다.

개념도로 줄이면 한 문장입니다. 같은 문의를 하나의 request_id로 장부, Jira, 실패 보관함에 이어 두고, 먼저 적고, 한 번만 바꾸고, 다시 확인하고, 실패하면 번호를 남깁니다.

구체적으로는 여섯 가지입니다. 사용자와 기록을 조회하는 API, 요청 상태를 적는 접수 대장 state, Jira 티켓을 다루는 handoff, 실패한 건을 보관하는 DLQ, 오류 처리 워크플로우 errors, 그리고 Discord 어댑터입니다. errors는 아직 초안입니다.

다른 역할과는 이렇게 맞췄습니다. R01은 서버와 DB, 봇 기동, 병합을 맡고 있습니다. R02 태경님과는 save를 한 번만 부르고, 완료 기록은 제가 Jira를 확인한 뒤에 하기로 했습니다. R03의 검색 근거는 응답에 같이 보여주고, R05의 시험은 결과에 맞춰 기대값을 바꾸지 않기로 했습니다.

슬라이드 2. 구현한 것

구현한 건 네 가지입니다.

첫째, 같은 요청이 두 번 처리되지 않게 했습니다. request_id를 처리권으로 쓰고, 저장은 prepare, bind, finish 세 단계로 나눴습니다. 시작을 먼저 적고, 티켓 번호를 연결하고, Jira를 다시 확인한 뒤에 완료로 적습니다. 같은 요청을 다시 보내도 새 티켓이 안 생기는 것은 팀 n8n에서 확인했습니다.

둘째, Jira 티켓 처리입니다. 같은 요청의 티켓이 있는지 먼저 찾고 없을 때만 만듭니다. 답변은 종료하고, 이관은 댓글과 담당 지정, 알림을 보냅니다. 종료 전환은 이름으로 찾고, 없으면 임의로 처리하지 않고 멈춥니다.

셋째, 부분 실패입니다. 티켓은 만들어졌는데 종료나 배정이 실패하면 partial_effect로 기록하고, 티켓 번호와 끊긴 단계를 남깁니다. PR #36의 첫 정상 시험이 담당 매핑이 비어서 이렇게 끝났는데, 번호가 남아 있어서 어디서 끊겼는지 바로 알 수 있었습니다.

넷째, Discord 접수입니다. /문의를 받으면 3초 안에 본인에게만 보이는 대기 상태로 바꾸고, R02 Webhook을 호출해서 비공개로 답을 돌려줍니다. 등록되지 않은 계정은 R02를 부르지 않고 거절합니다. 오류는 코드마다 다른 안내를 하고, 답이 길어도 접수번호는 남깁니다.

그 밖에 직접 연결해 본 것도 있습니다. n8n Webhook을 수동으로 추가하고, Discord와 Jira를 연동했습니다. Jira 자동화로 티켓 변화를 Discord 알림으로 보내 보기도 했고, 태경님 흐름을 HTTP로 불러와서 앞뒤에 제 노드를 붙여 봤습니다. 이 둘은 팀 시스템과 별도로 해 본 실습입니다.

[화면 설명: n8n 워크플로우, Jira 티켓, Discord 답변 캡처를 차례로 보여줍니다. 실서버 시험을 못 했다면 "이 화면은 로컬 시험입니다"라고 먼저 말합니다.]

슬라이드 3. 개념과 기술

개념과 기술은 따로 외우기보다, 우리 프로젝트에서 문의 한 건이 지나가는 순서에 대입해서 설명드리겠습니다. 시민이 Discord에서 "QR이 안 읽혀요, 자전거번호로 대여하는 방법을 알려주세요"라고 보낸 경우입니다.

첫째, /문의를 받으면 3초 안에 본인에게만 보이는 대기 상태로 바꿉니다. 필요한 권한만 쓰는 최소 권한이고, discord.py와 Docker Compose로 구현했습니다. 실제로 비공개 답변이 나온 것은 이 화면에서 확인했습니다.

둘째, Discord 계정을 두바퀴 사용자로 연결하는 사용자 매핑입니다. 등록되지 않은 계정은 R02를 부르지 않고 거절하고, 토큰이나 매핑 값은 코드가 아니라 환경 변수로 넣습니다. 이 동작은 어댑터 시험 22건으로 확인했습니다.

셋째, 같은 문의에는 같은 request_id를 붙여서 R02 Webhook으로 보냅니다. 같은 요청을 두 번 해도 결과가 같은 멱등성이고, n8n Webhook과 HTTP로 연결했습니다.

넷째, 접수 대장에 먼저 기록합니다. 처음 시작한 요청만 처리권을 갖고, 상태가 예상과 같을 때만 바꾸는 조건부 갱신을 씁니다. PostgreSQL과 n8n state 워크플로우로 만들었습니다.

다섯째, Jira입니다. 같은 요청의 티켓이 있는지 먼저 찾고 없을 때만 만들고, 종료는 전환 이름으로 찾아서 실행합니다. 이렇게 생성되어 완료로 옮겨진 티켓을 Jira 보드에서 확인했습니다.

여섯째, 종료나 담당 지정이 실패하면 partial_effect로 기록하고, 티켓 번호와 끊긴 단계를 실패 보관함에 남깁니다. PR #36의 첫 정상 시험에서 담당 매핑이 비어 있어 실제로 이렇게 끝났습니다.

일곱째, R03의 검색 근거와 문의 연결값을 붙여 본인에게만 답을 돌려줍니다. 마지막으로, 별도 실습으로 Jira 자동화를 이용해 티켓이 바뀌면 Discord 채널로 알림이 가게 만들어 봤습니다.

정리하면, 같은 요청이 두 번 들어와도 티켓은 하나, 중간에 끊겨도 번호는 남고, 실패하면 이어서 복구할 수 있게 만들었습니다. 이상입니다.
