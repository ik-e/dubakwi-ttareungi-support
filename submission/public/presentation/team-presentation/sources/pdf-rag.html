1. 원본 문서와 출처
공개 안내와 교육용 가상 정책을 구분합니다
수집과 정리
따릉이 앱 챗봇 메뉴·FAQ와 서울시·서울시설공단의 공개 안내를 참고했습니다. 원문·사진은 내부
보관하며 공개 저장소에는 조사 요약과 출처 링크를 둡니다.
시민용 6개: 대여, 반납, 고장·사고, 요금·환불, 계정·보안, 후속 문의. 담당자용 2개: 이관 정책, 티켓
처리 단계.
문서 특성
UTF-8 Markdown, 한국어 중심이며 제목·절·문단·목록으로 구성됩니다. 8개 문서 길이는 최소 405자,
중앙값 1,049자, 최대 2,385자입니다.
실제 안내와 교육용 가상 설정은 표시를 구분합니다. 실제 기관의 내부 정책 승인과 동일하지
않습니다.
갱신 및 권한
정기 갱신 주기는 미확정입니다. 정책 변경 시 출처·내용을 검토하고 버전과 해시를 갱신한 뒤 다시
색인합니다. 시민은 public, 허용된 담당자는 public과 restricted를 사용합니다.

2. 전처리와 청킹
청크는 검색할 수 있도록 나눈 작은 문서 조각입니다
전처리
수집한 안내를 주제별 Markdown으로 정리하고 출처·접근 수준·버전과 파일 해시를 관리합니다.
자동 HTML 추출을 구현한 것은 아닙니다.
나누는 기준
먼저 Markdown의 ## 주제 절을 나누고, 각 절 안에서 빈 줄로 구분된 문단을 청크로 만듭니다.
실제 안내와 가상 설정이 섞이지 않도록 분리합니다.
인접 문단을 복제하지 않아 전처리 기준 오버랩은 0자입니다. 표 머리글 반복이나 절차 단위 보호는
별도 구현하지 않았습니다.
측정 결과
기존 전처리 실측: 44개(public 36, restricted 8), 길이 최소 61자·중앙 124.5자·최대 251자. 토큰이
아닌 문자 수입니다.
절 전체를 합치는 구조는 41개였고 3개 절에서 실제·가상 정보가 섞였습니다. 공개 질문 13개 직접
임베딩 비교에서 두 방식 모두 기대 문서·절이 상위 3개 안에 포함됐습니다. n8n 종단 평가는
아닙니다.

3. 임베딩과 검색
의미를 숫자로 바꾸어 관련 문서를 찾습니다
모델과 차원
OpenAI text-embedding-3-large를 사용합니다. 과정의 기본 모델이며 한국어·영어 혼합 자료를
처리할 수 있어 선택했습니다. 로컬에서 벡터 1개의 길이 3,072차원을 확인했습니다.
다른 모델과 한국어 성능·도메인 적합성·실제 비용을 비교한 시험은 아직 없습니다.
검색 방식
문서 청크와 질문을 같은 모델로 벡터화하고 코사인 유사도로 비교합니다. 값이 클수록 의미가
가깝습니다.
저장소별 상위 5개를 찾고, 합친 결과에서 점수 0.30 미만을 제외한 뒤 최대 5개를 반환합니다.
0.30은 교육용 임시 기준입니다.
비용
2026-11-05 조사 기준 모델 입력 100만 토큰당 $0.13입니다. 실제 색인 토큰 수와 비용은 측정하지
않았습니다.

4. 저장·권한·메타데이터
검색에 필요한 정보와 접근 범위를 함께 관리합니다
현재 저장소
n8n Simple Vector Store는 벡터를 프로세스 메모리에 저장합니다. 공개·제한·준비 상태에 각각
dubakwi-demo-public, dubakwi-demo-restricted, dubakwi-demo-readiness 키를 사용합니다.
검색 전 권한 선택
시민은 public만, 서버에서 허용된 담당자는 public과 restricted를 검색합니다. 실제 사용자 확인은
R02의 B05와 R04 사용자 API를 거칩니다.
모의 요청으로 확인한 권한 분리는 실제 서버 인가의 전체 검증과 별개입니다.
근거 메타데이터
doc, title, section, chunk_id, access_level, type, version과 출처 정보를 보관합니다. 응답에는
문서·절·본문·점수·권한·버전 등을 전달합니다.
권한별 메모리 키는 소규모 논리 분리이며, 제품군 파티션이나 분산 샤딩은 미구현입니다.

5. 복구·운영 확장
원본을 보존하고 색인을 다시 만들 수 있어야 합니다
지금의 복구
원본 Markdown과 manifest, workflow를 Git으로 관리합니다. 메모리 저장소는 재시작 시 사라질 수
있어 수동 재색인이 필요합니다. 준비 전·실패 중에는 검색을 차단합니다.
로컬 재시작·재색인 복구를 시험했습니다. VM 재시작 복구와 다중 프로세스 공유·동시 색인은 별도
검증 전입니다.
향후 PostgreSQL 설계
Docker 기반 PostgreSQL과 pgvector를 후보로 검토합니다. R04의 상태·DLQ 저장과 RAG 벡터
저장은 다른 작업이며, DB 백업·복원 및 접근 권한을 별도로 시험해야 합니다.
3,072차원에서 사용할 인덱스·차원 축소·검색 품질·비용은 비교 후 결정합니다. 버전별 색인 전환과
롤백은 설계 단계입니다.
규모 증가
동일한 청크 분포를 가정하면 10배는 약 440개, 100배는 약 4,400개입니다. 색인 시간과 비용은
실제 측정값이 없어 추정하지 않습니다.

7. 11월 7일 검토와 후속 계획
시험 사실과 추가 검증이 필요한 내용을 나눕니다
검색 시간과 원인
R05 실행 #796에서 검색은 약 3,018ms로 3초 제한을 넘어 이관됐습니다. 임베딩·통신·검색 각각의
시간은 미측정이므로 원인은 확인되지 않았습니다.
지식과 답변 수정
PR #31의 지식 수정은 main에 병합됐습니다. R02의 답변 생성 규칙 수정은 별도입니다. VM
적용·재색인 시점은 R01의 최신 인계로 확인하고 새 실행으로 재시험합니다.
권한과 복구
로컬 모의 권한·청킹 검사 13건은 통과했습니다. 실제 서버 사용자 권한 종단, VM 재시작 복구와
PostgreSQL·pgvector 전환을 검증한 결과는 아닙니다.
시험 결과 해석
WF-01의 3회 개별 판정과 결과서 일부 합계 표현이 달라 R05에 확인이 필요합니다. 기존 실패
기록은 보존합니다.
