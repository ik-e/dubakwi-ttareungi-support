    • 구현에 필요한 개념과 기술

    1. 워크플로우 아키텍처와 오케스트레이션

    워크플로우는 여러 작업을 어떤 순서와 조건으로 실행할지 정한 흐름이다. 오케스트레이션은 검색, AI 답변, 티켓, 저장처럼 서로 다른 기능의 호출과 결과를 조정하는 역할이다. 저는 각 기능이 독립적으로 동작하는 것뿐 아니라, 앞 단계의 결과를 다음 단계가 올바르게 받아 처리하도록 전체 구조를 연결했다.

    일반 안내의 기본 흐름은 입력·검사 → 분류 → RAG·조회 → 답변 → 검증 → 티켓 생성·처리 → 저장·응답이다. 모든 문의를 같은 순서로 처리하지 않고 상황에 따라 필요한 단계만 거치도록 했다.

    2. n8n 노드와 조건 분기

    n8n에서는 Webhook으로 요청을 받고, Code로 입력·결과를 검사하며, If와 Switch로 경로를 나눈다. HTTP Request는 검색·조회·티켓 기능을 호출하고, Execute Sub-workflow는 상태 저장 같은 하위 흐름을 연결한다. 마지막에는 Respond to Webhook으로 정규화한 응답을 반환한다.

    분기에서는 우선순위가 중요했다. 긴급 문의는 보완이나 검색을 기다리지 않고 먼저 담당자에게 연결한다. 일반 문의의 정보가 부족하면 보완 질문을 하고, 서버에 저장된 보완 횟수가 한도에 도달하면 이관한다. 일반 안내의 티켓은 답변 검증 뒤에 생성·종료하도록 했다.

    3. LLM 역할 분리와 구조화된 출력

    LLM은 문의를 분류하는 triage, 허용된 근거로 답변하는 writer, 답변의 근거와 정책을 확인하는 verifier로 나눴다. 역할마다 입력과 JSON 출력 형식을 정하고, 임의로 권한을 부여하거나 업무 도구를 실행하지 않도록 했다.

    검증 모델이 통과라고 응답해도 곧바로 안내하지 않는다. B21 Code 노드에서 JSON 형식, 인용 근거, 개인정보 가림, 정책과 적용 범위를 다시 확인한다. 근거가 부족하거나 검증에 실패하면 담당자 이관으로 전환한다. 모델 검사와 Code 검사를 함께 사용하지만, 이것이 답변의 정확성을 완전히 보장한다는 뜻은 아니다.

    4. API·JSON 계약과 결과 정규화

    API는 다른 기능을 호출하는 접점이며, JSON은 요청과 결과를 주고받는 구조화된 데이터 형식이다. 본체는 검색의 SearchRequest/SearchResult, 티켓의 TicketRequest/TicketResult, 저장의 StateRef 등 공통 계약을 사용한다.

    단순히 HTTP 요청이 성공했는지만 보지 않고 실제 업무 효과가 확인됐는지 검사한다. 검색 결과가 없는 empty, 실행할 필요가 없는 skipped, 실패한 error를 구분하고, 티켓 결과에서는 생성·종료·배정·알림과 저장 여부를 각각 확인한다. 다른 담당자의 기능과 연결할 때 필드 이름뿐 아니라 성공과 실패의 의미까지 맞추는 것이 필요했다.

    5. 분기·병렬 구조와 보완·긴급 후속 흐름

    B13에서 준비한 요청은 B14의 RAG 검색과 B15의 본인 기록 조회로 갈라지고, B16에서 결과를 취합한다. 사용하지 않는 기능도 skipped 결과를 반환해 합류 조건을 분명히 했다. 다만 가지가 두 개라는 사실만으로 실제 동시 실행이나 처리 시간 단축을 주장할 수는 없다. 실행 순서와 시간은 실제 환경에서 확인해야 한다.

    보완은 같은 실행 안에서 무한 반복하는 방식이 아니라, 새 request_id와 같은 case_ref로 다음 요청을 받아 이어간다. 긴급 문의는 최초 티켓·알림 확인 뒤 검색·조회로 돌아와 초동 안내를 보완하되, 티켓 재생성·재알림을 반복하지 않도록 가드를 둔다.

    6. 상태 관리·멱등성과 저장 게이트

    request_id는 한 요청과 재전송을, case_ref는 이어지는 문의를 구분한다. 멱등성은 같은 요청을 반복해도 업무 효과가 중복되지 않도록 만드는 성질이다. 같은 소유자·입력의 완료 요청은 저장된 결과를 재사용하고, 처리 중이거나 효과 확인이 필요한 요청은 자동으로 전체 실행을 반복하지 않는다.

    외부 변경 전에는 의도를 저장하는 prepare, 생성이 확인된 티켓 ID를 연결하는 bind, 최종 결과를 저장하는 finish 경계를 지킨다. 본체의 최종 저장도 B31 → B37 → B38 → B39 → B32 순서로 준비 결과와 실행 허용 여부를 확인한다. 저장 계약의 내부 구현은 R04가 맡고, 저는 본체가 이 게이트를 건너뛰지 않도록 호출·분기·결과 검사를 연결했다.

    7. 시간 예산과 부분실패 처리

    문의 처리에는 전체 응답 기한과 각 기능의 실행 한도가 필요하다. 설계에서는 전체 20초 안의 응답을 기준으로 검색·모델·티켓·마무리에 시간을 배분한다. 모델만 오래 기다려 티켓 처리나 최종 저장 시간을 잃지 않도록 남은 시간과 예약 시간을 함께 고려한다. 이 값은 설계·구현 기준이며 전체 사례에서 실측 통과했다는 의미는 아니다.

    또한 명확한 실패와 성공 여부 미확인을 구분한다. Jira 생성 요청의 응답이 유실되면 실제로 생성됐을 수 있으므로 바로 다시 만들지 않는다. 확인한 ID와 효과를 보존하고 실패 상태·DLQ·운영 확인 경로로 연결한다. 자동 종료는 안내 제공 완료이고, 담당자 연결은 지정·알림 수락 확인이며, 실제 문제 해결이나 담당자 열람과는 다르다.

    관측 결과와 한계

  • 본체는 로컬 Code와 로컬 n8n에서 분류·검색·답변·검증·티켓·저장 연결을 시험했다. 실제 LLM·검색을 사용한 시험에서도 가짜 Jira·임시 저장소를 사용한 범위가 있으므로 실제 운영 연동 통과로 합산하지 않는다.
  • 2026-11-06 실행 305는 등록 사용자의 정상 문의 1건이 연결된 기록이다. R05는 n8n 화면에서 검색 근거와 답변의 일치를 확인했지만 Discord·Jira·DB 독립 조회는 R01 보고에 의존했다. 정상 1건으로 전체 분기·권한·중복·장애·복구를 검증했다고 말하지 않는다.
  • B17의 시간 판정과 모델 실행 한도는 사용자 지시에 따른 R01 대리 수정·통합 기록이 있다. R02 본체 설계와 공동 보완의 역할을 구분하며, 줄인 한도의 성능은 별도 실측이 필요하다.
  • 시민 답변에 내부 출처 설명이 섞이는 문제(F-S1-03)와 요금 문의의 보완 질문 문제(TC12)에 대한 로컬 수정·비교 기록이 있다. 확인한 기록 기준으로 VM 반영·R05 재시험 전까지 해결 완료로 표시하지 않는다.
  • 실패 문의의 자동 재개, 외부 효과 미확인 뒤의 복구, 실제 동시 요청의 중복 방지와 전체 시간 기준은 별도 검증이 필요하다. 워크플로우가 연결됐다는 사실과 모든 업무 효과가 안전하게 확인됐다는 사실을 구분한다.

    • 소감

    처음에는 워크플로우 설계가 기능을 순서대로 연결하는 일이라고 생각했다. 직접 구성해 보니 어떤 조건에서 다음 단계로 넘어가야 하는지, 언제 멈추거나 사람에게 연결해야 하는지를 정하는 일이 더 중요했다. 특히 일반 안내와 긴급 문의의 티켓 생성 시점을 다르게 설계하면서, 같은 기능도 실행 순서에 따라 사용자 경험과 업무 의미가 달라진다는 것을 배웠다.

    LLM이 답변을 만들었다고 해서 서비스가 끝나는 것도 아니었다. 근거와 정책을 검사하고, 티켓 처리와 저장이 확인된 뒤 어떤 수준의 완료를 사용자에게 안내할지 판단해야 했다. 정상 경로뿐 아니라 보완·검증 실패·응답 유실 같은 상황을 함께 설계하는 과정에서 안정적인 흐름의 중요성을 느꼈다.

    R03·R04·R05와 연결하면서 노드가 정상 실행되는 것과 전체 서비스가 올바르게 동작하는 것이 다르다는 점을 알게 됐다. 같은 성공이라는 표현도 검색 성공, 티켓 생성 성공, 결과 저장 성공이 각각 달랐고, 이를 구분해 기록해야 다른 담당자와 문제를 정확히 확인할 수 있었다.

    다음에는 구현 초기에 공통 요청·응답과 실패 사례를 더 구체적으로 맞추고, 부분실패·중복 요청·시간 예산을 함께 시험하고 싶다. 흐름도를 보기 좋게 만드는 데서 그치지 않고, 실제 실행 증거로 각 연결의 의미를 설명할 수 있는 설계를 하고 싶다.
