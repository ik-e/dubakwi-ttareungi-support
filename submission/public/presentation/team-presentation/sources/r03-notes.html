    • 구현에 필요한 개념과 기술

    1. RAG와 출처 관리

    RAG는 질문과 관련된 자료를 먼저 검색하고 그 결과를 AI의 답변 근거로 사용하는 방식이다. 자료의 출처·확인 시점·버전을 함께 관리하면 답변의 근거와 오래된 내용을 확인할 수 있다. 실제 따릉이 안내와 두바퀴의 가상 업무 정책을 혼동하지 않도록 [실제 안내], [가상 설정]을 구분했다.

    2. 전처리와 청킹

    전처리는 수집 자료를 주제별 Markdown으로 정리하는 과정이다. 청킹은 검색하기 쉽게 내용을 나누는 과정이다. ## 절과 빈 줄로 나눈 문단을 기준으로 하고 인접 문단은 중복하지 않았다(오버랩 0자). 2026-11-05 전처리 기준 44개, 길이는 최소 61자·중앙 124.5자·최대 251자였다. 토큰 수가 아니라 문자 수다.

    절 전체로 묶은 비교안은 41개였고 3개 절에서 실제·가상 정보가 섞였다. 공개 질문 13개를 직접 임베딩·코사인 방식으로 비교했을 때 두 방식 모두 기대 문서와 절이 상위 3개 안에 각각 13/13 포함됐다. 이 결과는 n8n 종단이나 최종 답변 품질 평가가 아니다.

    3. 임베딩과 유사도

    임베딩은 텍스트의 의미를 숫자 배열로 변환하는 것이다. text-embedding-3-large를 이용하며 로컬에서 3,072차원을 확인했다. 질문과 청크를 같은 방식으로 변환한 뒤 코사인 유사도로 비교한다. 상위 5개와 점수 기준 0.30은 초기 시연 설정이며 충분한 사례와 모델별 비용·성능 비교로 최적화한 값은 아니다.

    4. 저장소·권한·복구

    현재 시연은 n8n Simple Vector Store의 프로세스 메모리에 저장한다. 시민은 public, 허용된 담당자는 public과 restricted를 검색하도록 분리한다. 사용자 API→본체 B05→RAG 전달을 별도로 시험해야 하며 내부 호출자가 보낸 권한을 검색기가 신뢰하는 구조다.

    메모리는 재시작 시 사라질 수 있어 원본과 workflow를 보존하고 수동 재색인해야 한다. 색인 준비 전에는 답변에 쓰지 않도록 한다. 기존 메모리 키를 교체하므로 실패 후 즉시 버전 롤백은 구현되지 않았고, 보존한 이전 색인본의 전체 재색인과 검증이 필요하다. VM 복구 시험은 미실행이다. 향후 PostgreSQL·pgvector 전환은 계획이며, 현재 문의 상태용 PostgreSQL과 RAG 벡터 저장은 구분한다.

    5. n8n·API와 협업

    n8n은 문서 색인과 검색 호출을 연결한다. 검색 API는 내부 인증을 사용하고 요청 ID와 ok, empty, skipped, error 상태, 문서명·절·청크·점수·권한 등의 근거를 반환한다. R02는 본체의 요청·답변, R04는 사용자·저장 연결, R05는 사례 판정을 맡았다. 서로의 필드와 실패 의미를 맞춰야 전체 흐름이 동작한다.

    관측 결과와 한계

  • 11월 5일 VM 검색 단독 16건 중 14건 통과·2건 실패. 보안 초동 및 대여 실패·환불 질문의 근거가 미흡했다. 기존 기록을 보존하고 변경본 적용 후 검색 직접 호출과 P19 경유를 나눠 재시험한다.
  • 실행 305의 등록 사용자 정상 1건은 Discord부터 검색·답변·Jira·DB·비공개 응답까지 연결됐다. R05는 n8n 화면에서 public 근거 5건, 기대 QR 절 2위 및 답변 4문장의 근거 일치를 확인했고 Discord 화면·Jira/DB 독립 조회는 R01 보고에 의존했다. 전체 권한·장애·복구 통과를 뜻하지 않는다.
  • 시민 답변의 내부 출처 표현(F-S1-03)과 보완 질문(TC12)은 로컬 수정 후보가 있으나 VM 반영·R05 재시험 전까지 미해결로 구분한다. TC12는 검색을 거치지 않는 본체 보완 질문 경로다.
  • PR #31 지식·검색 변경은 main 병합됐으나 VM 재색인은 별도 조율 상태다. 원복 준비를 따른다.
  • R05의 WF-01 실행 #796에서 검색 응답이 약 3,018ms로 본체의 3초 제한을 넘어 담당자 이관됐다. 단계별 지연 시간은 측정되지 않아 실제 원인은 미확인이다. 로컬 모의 권한·청킹·워크플로 검사 13건은 통과했으며 인증 HTTP 7건은 내부 키 부재로 생략했다.
  • 위 검색 지연과 권한 분리는 R01이 사용 중인 VM 버전·시험 창을 확인한 후 R02·R05와 실제 권한 경로 및 반복 검색을 검증하도록 인계한다. VM의 현재 적용 상태를 확인하기 전에는 최신 지식이 적용됐다고 단정하지 않는다.

    • 소감 초안 · 본인 확인 후 수정

    처음에는 RAG가 문서를 검색하는 기능이라고만 생각했다. 직접 만들어 보니 어떤 자료를 믿을 수 있는지, 실제 안내와 가상 정책을 어떻게 나누는지, 검색된 문장이 시민에게 어떻게 전달되는지까지 함께 고민해야 했다.

    특히 자료 출처를 기록하려고 넣은 문장이 실제 답변에 섞였던 경험이 인상적이었다. 검색 결과가 맞더라도 사용자가 이해하기 쉬운 답변으로 이어지는지 별도로 확인해야 한다는 점을 배웠다.

    또한 다른 담당자의 사용자 확인·본체·저장 기능과 연결하면서, 내 기능의 로컬 성공과 전체 서비스의 성공을 구분하는 것이 중요하다는 것을 알게 됐다. 다음에는 사례를 더 다양하게 준비하고 재색인·복구 방법도 구현 초기에 함께 검증하고 싶다.
