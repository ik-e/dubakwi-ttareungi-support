두바퀴 발표 시연 절차 — 2026-11-09 리허설 반영

핵심 메시지: 안내할 수 있는 문의는 근거로 답하고, 확인이 필요한 문의는 정보를 보완해 담당자가 이어서 처리한다.

등록 계정의 Discord 데스크톱 앱에서 아래 질문 5개를 실제 전송했다. 반납 문의의 같은 Jira 맥락, 발표자 계정으로 할당, 진행 중 변경, 내부 메모 저장도 확인했다. VM 저장 응답과 감사 기록을 대조해 반납 세 번째 요청은 attempt_limit, 해외 이용 문의는 no_evidence로 이관됐음을 확정했다. Discord 봇의 실제 PR36 연결 경로도 확인했다. 상세 판정은 리허설 보고서와 서버 기록 대조를 따른다.

1. 준비할 화면과 입력 원칙

  1. 발표 8장 시민의 문의부터 담당자의 처리까지를 연다.
  2. Discord 데스크톱 앱에서 등록 계정으로 따릉이 민원소 → 따릉이-민원접수를 연다. Chrome 임시 계정은 등록 계정이 아니다.
  3. /문의 검색 결과에서 두바퀴 민원봇을 선택한다. 따릉이 민원봇 UX와 혼동하지 않는다.
  4. n8n R01 PR36 a657890 support → Editor를 구조 설명 화면으로 준비한다. Execute workflow 대신 Discord 명령으로 요청을 시작한다.
  5. Jira에 로그인하고 Queues → All을 연다. 현재 All은 완료·진행 중·대기 티켓을 모두 포함한다. 새 반납 티켓의 자동 배정 계정과 발표자 계정이 다르면 해당 가상 티켓의 나에게 할당을 사용한다.
  6. 예비 증거로 발표 8장의 과거 실행 기록 공개 텍스트의 원자료 13~14쪽을 준비한다. 11/06 보존 기록이며 오늘 요청의 실행 로그가 아니다.
  7. 모든 새 시연은 새 문의에서 시작한다. 이전 리허설의 case_ref를 새 시연에 재사용하지 않는다.

case_ref는 다음 입력을 이전 문의에 연결하는 값이고 Jira 접수번호와 다르다. 내용 입력 후 Tab → case_ref 옵션 선택 → 연결값 붙여넣기 → 내용과 연결값 확인 → Enter 순서로 전송한다. case_ref를 질문 문장 안에 넣지 않는다. 옵션 선택 전에 Enter를 누르면 별도 문의가 접수될 수 있다.

11/09 큐 확인: 사용자가 필터를 전체 조회로 바꾸고 이름을 All로 변경했다. 이후 읽기 전용 화면에서 Done·In Progress·To Do가 함께 표시됨을 확인했다. 큐의 일부 목록만 보고 티켓 존재 여부를 단정하지 않고, 현재 시연 답변의 접수번호로 검색하거나 상세를 연다. 이전의 미해결 큐 설명은 사용하지 않는다. 확인 기록.

시간 화면·동작 핵심

1:00–2:20 새 반납 문의 → 같은 case_ref로 두 번 보완 부족한 정보를 확인하고 같은 문의를 이어감
2:20–3:00 검색 근거 없는 새 문의 → 담당자 연결 근거가 없으면 답을 단정하지 않음
3:00–4:30 반납 티켓 → 맥락 → 나에게 할당 → 진행 중 → 내부 메모 담당자가 이어서 처리
4:30–5:00 보존 실행 증거 구분·발표 9장 복귀 확인 범위와 결과로 연결

시간은 편성값이다. 이번 작업에는 진단과 증거 수집이 섞여 있어 연속 5분 발표 실측이나 서비스 응답 시간으로 사용하지 않는다. 25초 대기 한도는 발표 진행 규칙이며 성능 SLA가 아니다.

3. 정상 QR 안내

  1. /문의를 선택한다.
  2. 내용에 아래 문장을 입력한다. case_ref는 비워 둔다.
QR이 안 읽혀요. 자전거번호로 대여하는 방법을 알려주세요.
  1. Enter로 전송한다.
  2. 답변의 자전거 번호 5자리 입력 안내와 출처를 가리킨다. 리허설 출처는 rental-guide / QR 인식 또는 잠금 해제가 어려운 경우였다. 문장 전체나 검색 점수를 읽지 않는다.
  3. n8n Editor에서 문의 분류 → RAG 검색 → 답변 생성 → 답변 검증을 가리킨다. 실제 노드 이름은 B10, B14, B19, B20이다. 번호는 조작용 메모로만 사용한다.

대본: “먼저 문서로 안내할 수 있는 질문입니다. 자전거 번호로 대여하는 방법과 출처를 함께 제공합니다. 내부적으로 질문을 분류하고 관련 근거를 찾은 뒤, 답변을 만들고 검증하는 구조입니다.”

확인: 비공개 응답, 실제 안내, 출처, 새 문의 연결값. Editor는 구조 설명이며 방금 실행한 경로의 색 표시가 아니다.

4. 반납 문의 — 보완 두 번 뒤 이관

첫 번째 요청

새 /문의의 내용에 입력한다. case_ref는 비워 둔다.

반납했는데 앱에 아직 이용 중으로 나와요.

리허설 응답: 자전거 번호, 반납 장소(대여소), 반납 시각, 잠금 상태를 요청했다. 반환된 연결값을 발표자 메모에 보관한다.

대본: “반납이 됐다고 단정하려면 정보가 부족합니다. 그래서 자전거 번호와 장소, 시각, 잠금 상태를 묻습니다.”

두 번째 요청

새 /문의 명령을 선택하고 내용에 입력한다.

따릉이 앱이고 자전거 번호는 기억나지 않아요.

Tab → case_ref 옵션 선택 → 첫 응답 연결값 입력 → 확인 → Enter. 리허설에서는 같은 연결값으로 보완 질문이 한 번 더 나왔다.

세 번째 요청

같은 방법으로 아래 문장과 같은 case_ref를 전송한다.

대여소 이름도 정확히 모르겠어요.

리허설에서는 “담당자 확인이 필요한 문의로 분류했습니다”와 Jira 접수번호가 나왔다. 그 접수번호를 반납 티켓으로 따로 기록한다.

대본: “추가 답변은 앞선 문의에 연결됩니다. 최초 문의를 포함해 세 번째 입력에 도달하면 보완 한도에 따라 담당자에게 넘깁니다.”

확인: 같은 연결값, 같은 Jira context의 attempt 1→2→3, waiting_info→waiting_info→handed_off. 세 번째 요청의 저장 응답과 B33 감사 기록은 reason=attempt_limit였다. 이번 정확한 입력 조합에서 관측한 결과이며 모든 질문이 같은 횟수로 이관된다는 보장은 아니다. 두 번째에 이미 이관되면 세 번째 입력을 생략한다. 세 번째에도 보완 질문이면 추가 제출하지 않고 리허설 준비 티켓으로 전환했다고 밝힌다.

발표자 주의: 최초 문의가 1회, 추가 답변 두 번이 각각 2·3회차다. 현재 코드는 attempt>=3을 필수 정보 부족 여부보다 먼저 검사해 세 번째 입력에서 정보를 모두 채워도 한도 이관이 우선한다. 3회는 자동 보완 한도이며, 이관 후 같은 문의에 추가 정보를 남기는 별도 경로와 구분한다. 긴급·사람 판단·근거 부족이면 더 일찍 이관될 수 있다.

5. 검색 근거가 없는 별도 문의

새 /문의를 선택하고 case_ref 없이 다음 문장을 전송한다. 앞의 반납 문의와 별개의 문의다.

따릉이를 해외 여행에 가져가서 한 달 동안 써도 되나요?

리허설에서는 가능/불가를 임의로 단정하지 않고 담당자 확인과 별도 Jira 접수번호를 반환했다. 같은 요청의 저장 응답은 route=담당자 이관, reason=no_evidence, sources=[]였고 B33 감사 기록도 같은 사유·HTTP 200이었다. 분류 단계의 needs_human 직접 이관과 구분해 확인했다.

대본: “이번 질문은 검색에서 답변에 사용할 근거를 찾지 못했습니다. 그래서 가능하다고 임의로 답하지 않고 담당자 확인으로 연결합니다. 앞의 반납 문의는 보완 한도 때문에, 이번 문의는 근거 부족 때문에 이관된다는 차이가 있습니다.”

검증 근거: B17의 검색 빈 결과 분기가 no_evidence로 이관한다는 구현과 실제 저장 응답·감사 기록을 대조했다. n8n 노드별 입출력을 저장한 것은 아니므로 live SearchResult 원문이나 점수까지 관측했다고 말하지 않는다. 검색 전용 status=empty 증거는 11/08 SR-WF03에 별도로 있다. 장애 주입·DLQ 생성·복구 장면으로 표현하지 않는다.

6. 담당자 Jira 처리

  1. “앞서 보완했던 반납 문의를 담당자 화면에서 이어 보겠습니다”라고 말한다.
  2. 반납 티켓을 연다. 직전 예외 문의의 접수번호와 혼동하지 않는다.
  3. 설명에서 최초 문제 요약을, 활동에서 이관 요약과 부족한 정보를 보여준다. 자동 AI Summary 대신 원래 설명·활동 기록을 기준으로 한다.
  4. 같은 티켓의 context revision 1/2/3과 보완 횟수 1/2/3은 리허설 검증 근거다. 발표에서는 JSON 전체를 읽지 않는다. Jira는 원문 대화 전체가 아니라 요약·사용자 진술·부족 정보 등 구조화된 맥락을 보존한다.
  5. 자동 배정 계정과 발표자 계정이 다르면 나에게 할당을 클릭한다. 현재 로그인 계정으로 담당자가 바뀐 것을 확인한다. 자동으로 발표자에게 배정된 것처럼 설명하지 않는다.
  6. 해야 할 일 - 상태 변경 → Start 진행 중을 선택한다. 이미 진행 중이면 상태만 확인한다.
  7. 활동 → 내부용 메모 추가를 클릭한다. 고객에게 회신을 선택하지 않는다.
  8. 아래 문장을 입력하고 저장한다.
발표용 가상 문의: 최초 문의와 추가 확인 내용을 검토했습니다. 실제 반납 변경이나 환불 조치는 수행하지 않았습니다.
  1. 메모 작성자·담당자·진행 중 상태를 함께 확인한다.

대본: “담당자는 최초 문제와 추가로 확인한 내용, 아직 부족한 정보를 이어받습니다. 이 가상 건을 제가 맡아 진행 중으로 바꾸고 내부 처리 메모를 남기겠습니다. 실제 반납 변경이나 환불을 수행한 것은 아닙니다.”

Jira 기능 범위: 문의 검토·담당자 지정·진행 중·내부 메모·완료/해결 전환까지 관리할 수 있다. 11/08 별도 시험에서 완료 전환 뒤 시민이 다시 조회해 종료 안내를 받는 흐름을 확인했다. 이번 리허설·5분 조작은 진행 중·메모 저장까지다. 실제 환불·요금 정정·강제 반납·잠금 해제, 내부 메모의 Discord 자동 전달은 시연한 기능에 포함하지 않는다.

7. 실행 기록과 종료

현재 Support의 Settings에서 성공·실패·수동 실행·진행 기록이 모두 Do not save다. Executions에 방금 요청의 상세 실행이 나타나는 것을 시연 전제로 삼지 않는다. 이 설정은 임의로 켜지 않는다. 별도의 업무 DB와 감사 기록은 다섯 리허설 요청 모두 남아 있었다.

리허설 요청 저장된 처리 결과 감사 기록
QR 안내 자동 답변, 출처 1건 HTTP 200, 정상 안내
반납 최초·첫 보완 각각 보완 질문 두 요청 모두 HTTP 200
반납 두 번째 보완 담당자 이관, 보완 한도 attempt_limit HTTP 200, 같은 이관 사유
해외 이용 질문 담당자 이관, 근거 없음 no_evidence, 출처 0건 HTTP 200, 같은 이관 사유

이 표는 11/09 리허설 기록이다. 이후 새 시연의 로그를 자동으로 갱신하는 화면은 아니다. DB의 completed는 해당 요청 처리가 끝났다는 뜻이며 Jira 티켓의 업무 완료를 뜻하지 않는다.

  1. 현재 요청은 Discord의 비공개 응답과 같은 Jira의 실제 맥락·상태·메모를 증거로 보여준다.
  2. 노드별 실행 예시는 발표 8장 과거 실행 기록 → 공개 텍스트의 원자료 13~14쪽을 연다.
  3. “이 화면은 11월 6일 보존한 정상 실행 기록이며, 방금 요청의 실행 로그와는 별도입니다”라고 먼저 밝힌다.
  4. 분류·검색·작성·검증·저장 흐름을 짧게 가리킨 뒤 닫는다.
  5. 발표 9장 시험 조건과 실제 결과를 함께 확인했다로 이동한다.

대본: “지금 본 사용자 흐름과 별도로, 어떤 시험을 했고 어디까지 확인했는지 결과를 정리하겠습니다.”

8. 멈춤과 대체 규칙

  • 25초 안에 최종 응답이 없으면 처리 성공을 말하지 않는다. 같은 요청을 다시 누르지 않고 준비된 해당 사례 화면으로 전환했음을 밝힌다.
  • 연결값이 없거나 거절되면 새 문의를 보완 성공으로 섞지 않는다. 준비한 동일 문의 사례를 사용한다.
  • 이미 이관된 반납 문의에는 보완 한도를 보여주기 위한 추가 입력을 하지 않는다.
  • Jira에서 다른 티켓이 열리면 처리 버튼을 누르기 전에 반납 요약과 접수번호를 다시 확인한다.
  • 권한 문제로 나에게 할당·상태 변경·저장이 안 되면 성공했다고 설명하지 않고 공개 리허설 기록과 당시 판정을 설명한다. 원문 화면은 로컬 보존본에 있다.
  • 이번 시연에는 장애 주입·서비스 재시작·재색인·티켓 완료·실제 환불·강제 반납을 넣지 않는다.

9. 필수 산출물 대응

장면 산출물 전달할 개념
QR 안내와 n8n 구조 노코드 워크플로우 설계서·RAG 아키텍처 설계서 역할 분담, 검색 근거, 생성과 검증
같은 문의의 보완 노코드 워크플로우 설계서 정보 부족 분기, 요청 간 반복, 문의 맥락
예외 문의와 검색 증거 RAG 아키텍처 설계서·실행 결과서 근거 부족의 처리, 기대와 실제 경로 구분
Jira와 실행 증거 워크플로우 실행 결과서 외부 효과, 담당자 처리, 관측 근거와 한계

가이드: 로컬 docs/guideline/source/student/08-SUBMISSION.md의 20분 구성·5분 시연과 docs/guideline/source/Req/KSM-REQ.md의 원본 시연 순서를 따랐다. 원본은 공개 제외 자료 안내에 따라 내부 제출 묶음에만 포함한다. 정상→보완→검색 근거 없음→이관·로그를 실제 문의와 저장·감사 기록으로 대조했다. 범위 밖의 API 장애·DLQ 복구까지 통과로 확장하지 않는다.
