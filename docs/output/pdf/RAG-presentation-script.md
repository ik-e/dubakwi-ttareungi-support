# 두바퀴 RAG 발표 대본

발표자: 장상옥

## 1. RAG 데이터 처리 과정
안녕하세요. 두바퀴에서 RAG를 담당한 장상옥입니다. 저희 RAG는 따릉이 관련 질문을 받았을 때 관련 문서를 찾고 그 내용을 답변의 근거로 활용하는 방식입니다. 따릉이 상담 자료를 수집하고, 전처리와 청킹을 거쳐 임베딩한 뒤 저장하고 검색하는 과정을 설명드리겠습니다.

## 2. 데이터 수집
먼저 따릉이 앱 챗봇에서 각 메뉴를 하위 메뉴까지 직접 확인하고 가이드 정보를 수집했습니다. 서울시와 서울시설공단의 공개 안내도 참고했습니다. 원본 사진과 글은 추후 대조를 위해 보관하고, 정리된 문서를 검색에 사용했습니다.

## 3. 여덟 개 주제로 정리
수집한 자료를 시민용 문서 6개와 담당자 문서 2개로 나눴습니다. 담당자 이관 정책과 티켓 처리 단계 두 문서는 실제 따릉이 내부 정책을 알 수 없어 가상으로 설정했습니다.

## 4. 전처리와 청킹
수집한 내용을 Codex를 이용해 주제별 Markdown 문서로 정리하고, 실제 안내와 가상 설정을 구분했습니다. 출처, 접근 권한, 버전과 파일 해시도 관리합니다.

청킹은 먼저 제목 아래의 주제별 절을 나누고, 그다음 각 절에서 빈 줄로 구분된 문단을 각각 청크로 만듭니다. 예를 들어 반납 실패 절 아래의 잠금장치 확인과 직접반납 안내를 문단별로 나눕니다. 이웃 문단을 중복해서 붙이지 않기 때문에 전처리 기준 오버랩은 0자입니다.

## 5. 청킹 방식 비교
문단 단위와 절 전체 단위를 비교했습니다. 문단 단위 청크는 전체 44개이고, 절 전체로 묶으면 41개입니다.

공개 자료를 같은 질문 13개로 비교한 결과, 두 방식 모두 기대 문서와 절이 상위 세 개 안에 들어왔습니다. 절 전체 방식은 실제 안내와 가상 설정이 섞이는 절이 세 개 있어 문단 단위 방식을 우선 사용했습니다. 이 비교는 직접 임베딩과 코사인 계산을 이용한 참고 시험입니다.

## 6. 임베딩과 유사도 검색
문서 청크를 OpenAI의 text-embedding-3-large 모델로 숫자 배열인 벡터로 변환했습니다. 로컬에서 확인한 벡터 한 개의 길이는 3,072차원입니다. 질문도 같은 방식으로 벡터로 바꾼 뒤 코사인 유사도를 비교해 관련 내용을 찾습니다.

## 7. 저장, 권한, 복구
현재는 n8n의 Simple Vector Store에 벡터를 메모리 형태로 저장합니다. 공개와 제한 저장 공간을 나누어 시민에게는 public만, 허용된 담당자에게는 public과 restricted를 검색하도록 구성했습니다. 실제 사용자 조회와 연결한 권한 종단 시험은 아직 남아 있습니다.

이후 팀 VM의 Docker 기반 PostgreSQL에 저장하고 pgvector로 벡터 검색을 연결하는 방향을 계획하고 있습니다.

## 8. 로컬 시험 결과
교육용 공개 질문 13개에서 기대 문서와 기대 절이 각각 검색 결과 상위 세 개 안에 모두 포함됐습니다. 일부 질문에서는 기대 절이 2위였습니다. 제한 문서 두 개를 각각 겨냥한 public 요청에서는 제한 문서와 확인용 문자열이 발견되지 않았습니다. 로컬 참고 결과이며 공식 판정은 아닙니다.

## 9. 다음 단계
앞으로 VM 재시작 후 재색인과 검색 복구를 확인하고, 사용자 조회 결과에 따라 시민과 담당자의 검색 권한이 정확히 전달되는지 통합 시험하겠습니다. 공식 사례로 최종 답변과 근거 표시를 검증하고, PostgreSQL과 pgvector 연결, 백업과 복구도 확인할 예정입니다.
