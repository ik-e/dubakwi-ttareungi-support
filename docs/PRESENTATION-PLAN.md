# 발표 구성과 슬라이드별 준비 계획

작성: 2026-11-02 / 동기화: 2026-11-03. 대상: 5명 팀, 최종 발표 20분·질의응답 5분. 본문 10장과 질의응답용 부록을 제안합니다. 실제 발표 파일은 아직 만들지 않았습니다.

공용 발표 파일·발표자 메모·리허설 기록은 `docs/project/presentation/`에 작성합니다. 제안서·설계·결과·실행 이미지는 [개발 산출물 관리](project/README.md)의 경로를 따릅니다. 이 계획 문서는 현재 위치에서 유지합니다.

팀 이름은 **두바퀴**, 기술 접두사는 **dubakwi**입니다.

이 문서는 **슬라이드에서 무엇을 설명하고 어떤 증거를 보여줄지** 정합니다. 현재는 구성안이며, Discord 시민 문의·Jira·최소 상태/실행 기록/DLQ·Docker Compose를 반영합니다. 발표자 역할 ID·공용 파일 형식·실행 결과는 미확정입니다. 설계 기준은 [시스템 v0.13](project/SYSTEM-DESIGN.md), [워크플로우 v0.14](project/WORKFLOW-DESIGN.md), [RAG v0.10](project/RAG-ARCHITECTURE.md), [저장소 v0.4](project/STORAGE-DESIGN.md)입니다. 발표 준비의 진행 상태는 [개발 작업 원장 P29](DEVELOPMENT-PLAN.md#5-작업-원장)에서 관리하고, 슬라이드별 상태를 별도로 복제하지 않습니다.

2026-11-05 R01이 [통합 발표 인계 초안](project/presentation/integration-brief.md)을 작성했다. 기존 부분 시험·로컬 검증과 미완료 종단/권한/성능을 구분한다. 발표자·최종자료·리허설은 아직 미확정이다.

## 1. 발표의 중심 내용

“따릉이 시민 문의를 정상 신규 건마다 Jira에 접수하고, 근거 안내·보완·담당자 연결로 처리한다”는 문제와 설계를 설명합니다. 구현 후에는 **어디까지 동작했고 어떤 시험으로 확인했는지** 보여줍니다.

따릉이에 기존 지원 채널이 없다는 전제를 사용하지 않습니다. 기존 앱·상담·신고 기능을 인정하고, 선택한 사례에서 어떤 맥락·권한·실패 처리를 연결했는지 설명합니다. 직원은 Jira 티켓을 받는 담당자이며 별도 직원/협업 업무 서비스는 범위 밖입니다. 시민 UI·실제 시민 인증·기관 시스템 연동 없이 모의 데이터로 검증한 MVP임을 명시합니다. 실제 기관 시스템 도입이나 업무 개선 효과를 검증한 것처럼 말하지 않습니다.

## 2. 발표자 1명과 자료 작성 역할

**사용자 결정: 발표자는 1명입니다.** 아래의 F는 한 명의 발표자를 뜻하며 모든 본문·중간 발표·시연 설명을 맡습니다. F는 R01~R05 중 역할 ID로 지정하며 80일차 2교시에 팀 헌장에 기록합니다. ① 팀장이 맡는 안을 우선 추천하지만 아직 확정한 것은 아닙니다. F는 여섯 번째 팀원이 아니라 기존 5명 중 한 명입니다.

| 구분 | 책임 | 발표 중 역할 |
| --- | --- | --- |
| 발표자 F | S01~10 전체 내용 숙지·발표자 메모·시간 관리·질의 응답 진행 | 혼자 전체 설명. 질문의 기술 근거는 담당자 메모를 받아 F가 전달 |
| ① 팀장·통합 | S01~02 내용, 공용 발표 파일의 최종 편집·버전·출처 표기 | F가 아니면 진행 지원. 발표자는 자동으로 팀장으로 확정되지 않음 |
| ② 오케스트레이션 | S03~04의 업무 흐름·공개 계약·실제 입출력 제공. S03 전체 구성/배포는 R01, 저장 관계는 R04가 지원 | 기본적으로 발언 교대 없이 근거 지원 |
| ③ RAG | S05~06의 문서·권한·설정·측정 표·복구 설명 제공 | 기본적으로 발언 교대 없이 근거 지원 |
| ④ 연동·안정성 | S07~08의 Jira 생애주기·요청 상태·DLQ·부분실패·복구 증거 제공. 조작/시간표는 R05와 합의 | 기본적으로 발언 교대 없이 근거 지원 |
| ⑤ 시험·품질 | S09~10의 결과·실패·보고서 검증, 시연 조작 | F가 설명하는 동안 말없이 화면·요청 조작. F=⑤이면 직접 조작하거나 다른 1명을 헌장에 배정 |

발표자 1명과 자료 작성자 5명을 구분합니다. 각 담당자는 자신의 슬라이드에 **핵심 설명 3문장·그림/표·증거 경로·예상 질문 2개와 답변**을 제공하며, 발표용 원고를 각자 따로 발표하지 않습니다. 질의응답도 F가 진행합니다. 담당자의 직접 답변이 필요한 운영 방식은 추후 사용자 결정이 있을 때 변경합니다.

발표 형식·도구·파일명은 미정입니다. 확정되면 P29 증거 칸과 이 문서에 실제 경로를 기록합니다. ①이 편집하는 시간에 기술 담당자는 자료 검토를 넘겨받고, F의 연습 시간에는 필수 구현 작업을 동시에 배정하지 않습니다.

## 5. 5분 시연 구성안

아래 파일명은 용도를 설명한 것이며 아직 미정입니다. 확정된 `requests/` 파일·사례 ID·보고서·고장 설정/복원 방법을 `README.md`와 결과서에 기록합니다. 원본 요구의 시연 순서는 예시이며, 아래는 이를 발표 시간에 맞춘 제안입니다.

| 구간 | 시연 내용 | 보여줄 화면·판정 | 원본 순서 대응 |
| --- | --- | --- | --- |
| 0:00~1:30 | S1 근거 안내 1건 | 분류/RAG/답변/검증·출처, Jira 생성/안내 종료·최종 저장 확인. 비이관 응답 ticket=null과 내부 티켓 구분 | 1~3 |

Discord 기본 시연은 slash command/defer/비공개 최종 응답을 보여주고, 공통 장애 주입은 Webhook/data-api 경로와 구분한다. 봇 미준비 시 검증된 팀 Webhook 시연을 사용하고 Discord 연결 성공으로 표현하지 않는다.

시연 시작 전 가이드의 doctor/ready·fault all ok·llm up 절차가 팀 도구에 맞게 동작하는지 확인합니다. Jira와 data-api의 고장 주입 경로를 R04/R05가 P25에 명시하며 Jira에 과정 fault 명령이 적용된다고 가정하지 않습니다. data-api/모의 경로를 사용하면 화면과 설명에 표시하고 Jira 성공 증거와 구분합니다.

S3 성공 이관·S4 본인/타인 조회·S5 긴급 및 저장 실패/재처리는 전체 시험·부록 증거로 준비합니다. 5분 안에 모두 실시간 실행하려고 범위를 늘리지 않습니다. 검색 결과 없음과 성공한 티켓 이관은 별도 시험·대표 로그도 준비합니다. 실시간 시연이 실패하면 관찰된 실패를 설명하고, 사전에 저장한 **해당 버전·환경·시점의 실행 증거**로 전환합니다. 캡처나 녹화를 실시간 성공처럼 표현하지 않습니다. 대체 증거가 VM 시연 요건을 대체한다고 간주하지 않으며 리허설에서 정상 실행을 확인합니다.

발표 자료의 형태는 ①이 먼저 만들고, ②~⑤가 기존 설계·보고서에서 그림·표·증거를 제공하는 방식입니다. 자료를 82일차에 처음 만드는 계획이 아닙니다. ①의 편집 예약은 80일차 15분·81일차 20분·82일차 기본 20분과 수정 최대 20분이며, 담당자 콘텐츠 작성은 기존 산출물 작성과 연결합니다. 이 시간은 충분함이 검증된 추정치가 아니라 팀이 확보할 최소 작업 창입니다.

### 시간 확보를 확인하는 조건

- **81일차 발표②까지** 공용 파일 S01~08의 초안이 있고, S09~10은 보고서 삽입 위치와 설명 틀이 있어야 합니다. 없으면 82일차 20분 편집만으로 완성 가능하다고 보지 않습니다.
- **82일차 10:20까지** 연습 가능한 한 파일·원고·시연 입력이 있어야 합니다. 최종 수치가 늦더라도 임시 수치를 만들지 않고 해당 장을 측정 대기로 표시합니다.
- 연습은 **설명·시연 19분 목표/20분 이내, 질의 연습 5분**입니다. F가 혼자 핵심 판단과 실패 원인을 설명할 수 있어야 합니다. 두 번의 연습 시간은 각각 내부 25분과 공식 배정 25분입니다.
- F가 ②~⑤이면 리허설 시간의 기술 업무는 전날까지 정리합니다. 결함으로 연습이 중단되면 ①이 작업 우선순위를 조정해 같은 날 연습 시간을 다시 확보합니다. 사람 한 명을 구현·연습에 동시에 계산하지 않습니다.
- 지연 시 부록의 꾸밈·추가 화면·추가 사례를 줄이고 필수 증거·19분 원고·VM 시연을 우선합니다. 필수 시험을 생략해 시간을 확보하지 않습니다.
- 최종 증거가 연습 때와 달라지면 해당 슬라이드와 원고를 F가 다시 확인합니다. 최종 파일 경로·버전·연습 실제 소요 시간은 P29 증거 칸에 기록합니다.

중간 발표도 F 한 명이 설명하고 ⑤가 조작합니다. 첫날은 범위·설계·골격·색인, 둘째 날은 구현·보안/장애·시험 결과를 중심으로 같은 자료에서 발췌합니다. 미완료 부분은 계획이라고 표시하며 당일 피드백은 데일리에 기록합니다.

최종 검토에서는 **계획/가정, 실제 구현, 실행으로 확인한 결과, 미해결 한계**를 구분하고 결과 숫자는 실제 보고서에서만 가져옵니다. 이 문서 작성 자체를 P29의 발표 자료 완성이나 연습 완료로 처리하지 않습니다.
