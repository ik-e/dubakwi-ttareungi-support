- 화면 내용:

  - 흔들림 1건: WF-01 정상 문의(FAIL → PASS → FAIL)
  - 실패 2건: TC12(애매한 문의의 보완 항목), TC14(이관 뒤 후속 요청)

### S10-1. 대표 실패: 정상 문의가 끝까지 처리되지 않음 → 수정 → 통과

| 단계 | 내용 |
| --- | --- |
| 현상 | 첫 실행(#266)은 Jira 안내 종료에서 멈춰 이관(`partial_effect`), 재시험(#279)은 답변 작성 전에 이관 |
| 원인 | #266: Jira에 완료 전환이 없음. #279: 남은 시간 15,120ms가 작성·검증에 필요한 15,500ms보다 작음 |

- 발표자 메모: "실패를 숨기지 않고 실패 실행 두 건을 그대로 보존했습니다. 원인을 고친 뒤 같은 질문으로 다시 돌려 통과를 확인했습니다."

### S10-2. 두 번째 실패: 중복 요청 시험을 판정하지 못함 → 입력 보완 → 통과 (부록 A05)

- 현상: 중복 요청 시험의 첫 요청이 이관되지 않고 보완 질문으로 끝나 중복 처리를 판정할 수 없었다(2회 같은 결과).
- 원인: 시험 입력에 결제일·이용권·결제 수단이 없었다. 시스템은 설계대로 정보를 더 물었다(시험 쪽 문제).
- 조치: 질문 문장만 보완했다. 기대 결과는 바꾸지 않았고, 바꾼 이유를 사례 파일에 기록했다.
- 재시험: 두 번째 요청이 같은 티켓을 `duplicate: true`로 0.3초 만에 돌려줬다. n8n 화면에서 분류(LLM)·티켓 생성 노드가 실행되지 않은 것도 확인했다(실행 #849).

### S10-3. 남은 한계

1. **이관 뒤 후속 요청**(TC14): 이관된 건에 정보를 더 보내면 다시 보완 질문으로 돌아간다. 5번 모두 같다. 설계 대조 중이다.
2. **검색 3초 제한**: 검색이 3초를 넘기면 정상 문의도 이관된다(#796, 3,018ms).
3. **검증 범위**:
   - 고장 3유형과 조회 2유형은 미실행이다.
   - 실제 시민 인증과 기관 시스템은 연동하지 않았다. 사용자와 접수 건은 모의 데이터다.
4. **보안 발견**: n8n 실행 기록에 팀 키가 평문으로 남는다. 저장 범위 조정을 검토 중이다.

- 발표자 메모: "남은 한계는 결과서 4절과 1.4절에 그대로 적었습니다. 시험하지 않은 것을 통과로 말하지 않습니다."

### S08 시연에서 R05가 할 일

- 발표자가 설명하는 동안 화면을 조작한다. 시연 순서는 `requests/demo-sequence.json` 7단계(정상 → 보완 질문 → 장애 → 이관·로그)다.
- 장애 시연(`demo-3-ticket-down.json`)은 Jira 고장 사본이 있어야 한다. 준비되지 않으면 이 단계는 실행 #796(검색 시간 초과 → 안전 이관) 화면으로 대체한다. 이때 저장된 화면이라고 말한다.
- n8n 실행 화면을 띄울 때 **B01 문의 수신 출력은 열지 않는다**(팀 키가 보임).

## 2. 시험에 필요한 개념·기술

| 개념·기술 | 무엇인가 | 이번 프로젝트에서 쓴 곳 |
| --- | --- | --- |
| 기대 결과 먼저 쓰기 | 만들기 전에 "이렇게 나와야 한다"를 정하고, 결과를 본 뒤 기대를 고치지 않는다 | `cases/` 사례 파일. TC12는 기대 단어가 부족했지만 실패로 남겼다 |
| 계약 칸으로 판정 | LLM 답 문장은 매번 다르므로 `route`·`sources`·`ticket`·`security` 같은 응답 칸으로 판정한다 | 모든 사례의 `expect`·`assert` |
| 공통·팀 시나리오 | 모든 팀이 같은 14유형 + 우리 설계를 보여 주는 팀 사례 5개 이상 | 공통 17건, 팀 24건 |
| 3회 반복과 흔들림 | LLM이 들어간 시나리오는 3번 돌려 모두 같아야 통과. 다르면 원인(LLM 판단·시간 초과·외부 지연)을 적는다 | R1~R3 반복, WF-01 흔들림 분석 |
| p50·p95 | 처리시간을 평균 대신 중앙값과 상위 5% 값으로 본다 | WF-01 5회 측정 |
| 장애 주입과 복원 | 고장 스위치를 켜고 시험한 뒤 반드시 끈다. `before`·`after`로 자동화 | 사례 파일에 설계, 고장 사본이 없어 미실행 |
| 중복 요청과 멱등성 | 같은 `request_id`는 저장된 결과를 그대로 돌려주고, 내용이 다르면 409로 거절한다 | WF-09, TC03 |
| 다단계 사례 | 앞 응답의 값(연결값)을 다음 요청에 넣어 보완 왕복을 시험한다 | TC01·TC01b·TC14 |
| 시험 도구 | `scripts/test/run_cases.py`: 사례 실행, 판정, 공통 검사(G01~G06), 로그 검사(L01~L03), 결과 저장 | 모든 VM 시험 |
| 공개 기록과 원시 기록 분리 | 원시 응답은 VM에만, 공개 기록은 Jira key·연결값·키를 가린 요약만 | `runs/<ID>/`와 `runs/public/<ID>/` |
| 해시로 같은 파일 확인 | VM 원본과 저장소 파일의 SHA-256을 비교해 옮기다 바뀌지 않았는지 확인 | 모든 결과 파일 |
| n8n 실행 화면 읽기 | Executions·Logs에서 실행된 노드, 분기, 노드별 시간, 오류 출력을 본다 | 대표 로그 3건, 단계별 시간 |
| Git 작업 규칙 | `<역할>/<P번호>-<내용>` 브랜치, `P번호: 목적` 커밋, 검사·미실행 기록 | R05 브랜치 3개 |

## 3. 소감 + 기타

> 아래 소감은 초안입니다. 본인 말투와 실제 느낌에 맞게 고쳐 주세요.

### 소감 (초안)

- "기대 결과를 먼저 쓰고, 결과에 맞춰 고치지 않는다"는 규칙이 처음에는 답답했습니다. 그런데 TC12와 중복 요청 시험에서 실패를 그대로 남겨 두니, 시스템 결함과 시험 입력 문제를 나눠 볼 수 있었습니다. 실패 기록이 가장 쓸모 있는 증거라는 말을 직접 겪었습니다.
- 같은 질문도 11번 중 2번은 다르게 나왔습니다. LLM이 들어간 시스템은 한 번 통과로는 아무것도 말할 수 없고, 반복과 원인 분석이 시험의 핵심이라는 것을 알게 됐습니다.
- 숫자를 보고서에서만 옮기는 원칙 덕분에, 결과서의 모든 숫자를 누가 물어도 어느 실행에서 나왔는지 바로 답할 수 있게 됐습니다.
- 증거 화면을 캡처하다가 팀 키가 찍힌 일이 있었습니다. 증거를 남기는 일 자체도 보안 위험이 될 수 있다는 것을 배웠고, 그 덕분에 실행 기록에 키가 남는 문제를 찾았습니다.
- 아쉬운 점은 고장 시험과 조회 시험을 하지 못한 것입니다. 시험은 다른 역할의 준비에 기대는 부분이 많으니, 필요한 사본과 데이터를 더 일찍 구체적으로 요청했어야 했습니다.

### 기타

- 미해결 사항과 확인 요청은 [실행 결과서](../EXECUTION-RESULT.md) 4절·6절에 정리했다.
- 새 버전이 VM에 배포되면 3회 반복과 처리시간 측정을 다시 돌려 S09 숫자를 갱신한다. 명령은 그동안 쓴 것과 같다.
- 발표 화면에 쓸 실행 캡처 17장은 결과서 PDF 부록에 있다(팀 키·식별자 가림).
