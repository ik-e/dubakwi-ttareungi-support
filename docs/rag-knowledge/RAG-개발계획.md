# R03 RAG 담당 개발 계획

작성일: 2026-11-04. 범위: 3일 프로젝트의 R03 담당. 팀 작업 원장과 [RAG 설계](../project/RAG-ARCHITECTURE.md), [워크플로우 계약](../project/WORKFLOW-DESIGN.md)이 우선 기준이며, 아래는 실행 계획이다. 현재 실제 색인·검색·통합·측정은 완료되지 않았다.

## 목표와 역할

시민 질문에 권한에 맞는 검토된 근거를 검색해 문서·절·출처와 함께 업무 워크플로우에 전달한다. 답변 생성·실제 신고 접수·Jira 처리와 시민의 실제 상태 판정은 RAG 담당 범위가 아니다. R02와 검색 계약, R04와 권한, R05와 평가를 맞춘다.

## 1일차: 지식 확정과 색인 준비

1. `docs/rag-knowledge/`의 6개 초안을 주제별로 검토한다. 원문 보관 HTML과 검토 전·상충 정보는 색인하지 않는다. 실제 안내와 두바퀴 가상 예시를 분리하고 출처·확인일·적용 조건을 보존한다. 보험과 유효기간 등 미확인 조건은 확정 답변에서 제외한다.
2. 팀 설계의 `knowledge/public/` 공개 6개와 `knowledge/restricted/` 담당자용 모의 정책 2개를 준비한다. 가상 정책은 실제 따릉이 규정이 아니라는 표기를 각 청크에도 보존한다. 권한 모델과 이관 자료는 R04와 확인한다.
3. `knowledge/manifest.json`에 문서 ID, 경로, 출처, 확인일, 버전, 승인 상태, 권한 및 원본 해시를 기록한다. R04·R05 검토를 받은 자료만 색인 대상으로 설정한다. 문서와 manifest 형식은 구현 시 RAG 설계에 맞춰 확정한다.
4. 최소 10개의 평가 질문과 기대 문서·절을 R05와 먼저 정한다. 예: QR 대여, 반납 미완료, 기본 대여시간, 환불 신청, 고장·방치, 사고, 분실물, 근거 없음, 권한 제한.

완료 기준: 승인된 목록과 미확인 목록이 구분되고 시민용 문서에서 내부 가상 정책이 검색되지 않는 권한 기준이 합의됨. 승인되지 않은 항목은 계속 제외한다.

## 1일차 상세 실행 계획 — 미진행

이 절은 작업 착수 전 계획이다. 요청에 따라 이 단계에서는 코드·워크플로우를 작성하거나 색인을 실행하지 않는다.

| 순서 | 작업 | 산출물 및 확인 기준 |
| --- | --- | --- |
| 1 | 6개 초안과 원본을 대조하고 절별로 출처·확인일·대상·확인 상태를 정리한다. 이용권 유효기간, 비회원 취소, 보험 조건 등 상충·미확인 항목은 표시한다. | 검토 목록: 사용 가능 후보, 확인 필요, 제외 및 이유. 최신 정책을 단정하지 않는다. |
| 2 | 시민 안내용 6개를 `knowledge/public/`에 정리한다. 대여·반납·고장/사고·요금/환불·상담·계정/보안을 각각 최소 3개 절로 작성한다. | Markdown 6개: 각 절에 출처·확인일·적용 범위. 상담원 확인이 필요한 사실은 추측하지 않는다. |
| 3 | 담당자 제한용 2개를 `knowledge/restricted/`에 작성한다. 문의 이관과 티켓 상태·처리 예시는 프로젝트용 모의 정책임을 명시한다. | Markdown 2개: 실제 기관 절차와 구분, 시민용 자료에 제한 내용 혼입 없음. |
| 4 | `knowledge/manifest.json` 초안을 준비한다. 문서 ID·경로·권한·가상 여부·출처·확인일·버전·승인 상태·내용 해시를 기록한다. 스키마와 권한 값은 팀 설계와 확인하고 예시 값을 확정 계약으로 단정하지 않는다. | 문서 8개와 manifest가 서로 일치. R04/R05 검토 전은 승인 대기로 표시하고 색인 대상에 포함하지 않는다. |
| 5 | 평가 질문 10개 이상과 기대 문서·절·조건을 작성한다. 일반 질문 외에 정보 없음, 실제 상태 확인 불가, 긴급 문의, 제한 문서 접근을 포함한다. | 평가 목록: 질문, 호출 권한, 기대 근거/없음, 답변 시 주의점. 측정값은 실행 전이므로 기재하지 않는다. |
| 6 | 문서 간 충돌, 공백·링크, 개인정보 및 원문 분리 여부를 점검하고 R02·R04·R05에 검토할 항목을 정리한다. | 점검 결과와 남은 의존성 기록. 사용자에게 1일차 산출물과 검토 대기 항목 보고. |

예상 소요: 문서 검토 1~2시간, 8개 문서 작성 2~3시간, manifest·평가 질문 1~2시간, 점검 및 인계 1시간. 실제 상황에 따라 조정한다. 작업 순서는 충돌 검토 → 문서 작성 → manifest → 평가 목록 → 점검이며, 사용자 요청에 따라 현재는 계획만 작성한다.

**팀 검토 대기:** R04의 권한·제한 정책 검토, R05의 예상 근거 및 평가 검토, R02의 검색 입출력 계약 확인은 실제 피드백이 오기 전에는 완료로 표시하지 않는다. 팀원이 검토하기 전에도 문서 초안과 점검 목록은 작성할 수 있다.

## 2일차: 색인·검색 구현과 통합

1. `workflows/dubakwi-index.json`을 구현한다. 승인 manifest만 읽고 제목·절·출처·권한을 보존해 청크와 버전별 공개/제한 색인을 만든다. 표·절차의 조건이 분리되지 않는지 점검한다.
2. `workflows/dubakwi-search.json`을 구현한다. 서버에서 결정한 권한으로 검색 범위를 먼저 제한하고 검색 결과에 문서, 절, chunk_id, 점수, 버전 및 출처를 포함한다. 시민 요청의 자칭 역할로 권한을 부여하지 않는다.
3. R02와 SearchRequest/SearchResult 계약을 맞춘다. `ok`·`empty`·`skipped`·`error`를 구분하며, 검색 실패와 근거 없음을 혼동하지 않는다. 개인별 대여·티켓 상태는 업무 조회에서 다룬다.
4. 동일 질문으로 절 단위와 고정 길이 청킹, top-k 후보를 비교하고 hit@k와 청크 분포를 측정한다. 임베딩 모델·차원·비용·지연은 사용 가능한 환경에서 실측한다.

완료 기준: 공개 질문에 근거가 반환되고, 무관 질문은 empty, 색인 미준비·장애는 error, 제한 문서는 시민 검색에서 제외됨. 실제 실행 결과를 남긴다.

## 3일차: 평가·복구·인계

1. R05와 정상·근거 없음·상충 자료·긴급 문의·권한 위반·검색 실패 시험을 실행한다. 근거 없는 금액·보험 보장이나 실제 접수 완료를 답변하지 않는지 통합 확인한다.
2. 재색인·인덱스 전환과 실패 복구를 시험한다. 새 버전의 문서 수·검색 결과를 검증한 뒤 전환하며 실패 시 이전 버전을 유지한다. 저장소의 실제 영속성과 재시작 동작을 측정한다.
3. [RAG 설계](../project/RAG-ARCHITECTURE.md)에 실제 선택한 모델·청킹·권한·결과·비용·한계를 기록하고, R02에 검색 입출력 예시와 실패 처리를, R05에 평가 결과를 전달한다.
4. 발표에는 출처, 권한 분리, 질문별 근거와 실제 측정 수치를 사용한다. 미실행 항목은 계획으로 표시한다.

완료 기준: 팀의 대표 시나리오에서 검색 근거와 권한을 확인하고, 검증 결과·복구 방법·남은 한계가 팀 문서에 기록됨.

## 상담 확인이 필요한 항목의 교육용 처리

아래는 **가상 시연 방침**이며 따릉이의 실제 운영정책이 아니다. 수치나 확정 판단을 만들어 넣지 않는다.

- 보험: 최신 계약·보장과 개인별 심사는 확인되지 않았다는 응답과 가상 담당자 이관을 시연한다.
- 유효기간 충돌: 공식 약관과 자료 간 차이·권종 예외를 제시하고 개인 사례는 가상 담당자에게 이관한다.
- 분실물·습득물: 마지막 이용 대여소·시각 등 필요한 정보를 수집해 가상 문의를 남긴다. 실제 접수나 보관 장소를 만들어 말하지 않는다.
- 방치신고·상담시간·마일리지: 실제 화면이나 운영 기준을 확인하지 못한 항목은 미확인으로 표시하고 문의 경로 안내 또는 가상 이관을 시연한다.

## 팀원과 맞출 항목

- R02: 검색 요청·응답 계약, 근거 없음/실패 시 업무 분기, S1 통합 시점.
- R04: 서버의 시민·담당자 권한 결정, 공개·제한 색인 분리, 가상 정책 범위.
- R05: 기대 근거·검색 평가 질문, 권한 누출·실패·재색인 시험 및 증거.

## 2026-11-04 1일차 작업 현황

P08의 지식 8개 초안·manifest·충돌 검토·평가 질문 20개를 작성했다. 문서별 가상 설정을 표시했으며 실제 자료 확인이나 팀 승인을 대신하지 않는다. [검토·평가 초안](day1-review-and-evaluation.md)을 참조한다. R04/R05 검토, 검색·색인 구현, 검색 및 권한 시험은 미완료다.

## 색인·검색 기능 상세 구현 계획

사용자 결정: 시민은 공개 6개, 담당자는 공개 6개와 제한 2개를 검색한다. 실제 안내와 두바퀴 가상 설정은 검색 근거와 답변에 각각 표시한다. 아래는 실행 전 계획이며 검색 결과를 확인한 것이 아니다.

1. **입력·환경 확인:** n8n 인스턴스·노드·저장 경로·임베딩 자격 증명·서버 역할 매핑 및 영속성을 확인한다. 실제 가능한 기능과 제공된 자료의 재사용 여부를 기록한다. 문서의 승인 상태·색인 허용 조건과 시연 모드를 명확히 한다.
2. **색인 P10:** `workflows/dubakwi-index.json`에서 manifest와 8개 경로·해시·권한을 검증한다. 제목·절 중심으로 분할하고 각 청크에 실제 안내/가상 설정, 출처·확인일·범위를 붙인다. 혼합 청크는 분리한다. 시민용·제한용 컬렉션을 분리하고 원문 HTML은 넣지 않는다.
3. **검색 P16:** `workflows/dubakwi-search.json`에서 서버가 확인한 시민·담당자 권한에 따라 컬렉션을 선택한다. 시민은 공개만, 담당자는 공개와 제한 모두를 검색한다. 중복을 정리하고 문서·절·유형·출처를 보존하며 `ok`/`empty`/`skipped`/`error`를 구분한다.
4. **표시·연결:** 현재 Evidence 계약과 R02 본체에서 근거 유형을 잃지 않도록 연결한다. 실제 안내와 가상 설정이 함께 있으면 문장별로 표시한다. 전용 필드가 필요하면 R02·R05와 계약·테스트를 함께 갱신한다.
5. **시험·측정:** [기대 결과 문서](search-expected-results.md)의 28개 사례로 공개/제한 접근, 문장별 표시, 근거 없음·오류·색인 미준비를 시험한다. 같은 질문으로 청킹 2가지와 top-k 후보를 비교해 검색 성능·지연·비용을 실측한다. 인증 실패·권한 위조·인덱스 재시작도 확인한다.
6. **복구·인계:** 새 색인을 검증한 뒤 활성 버전을 바꾼다. 실패 시 기존 버전을 유지하고 재색인 방법을 기록한다. 실제 모델·차원·설정·시험 결과와 미완료 사항을 RAG 설계·팀 시험 담당에게 인계한다.

완료 기준: 승인된 자료만 색인되고, 시민·담당자 검색 범위와 실제/가상 구분이 검색과 최종 응답에서 검증된다. 테스트 수치와 실행 결과는 실제 실행 후 기록한다.
