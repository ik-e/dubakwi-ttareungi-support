# R03 시험 결과 검토와 인계 · 2026-11-07

범위: R05 실행 결과서 v0.8과 발표 자료, R02 워크플로우 자료, PR #31·#36의 공개 기록. **과거 시험 기록과 현재 운영 상태는 별개**다. 이 검토는 공용 VM·Jira·DB·DLQ 변경이나 신규 VM 실행을 포함하지 않는다.

## R05 실행 결과서에 대한 R03 확인

1. **검색 시간 초과:** R05의 WF-01 실행 #796은 B14 제한 3,000ms를 넘겨 약 3,018ms에 검색 시간 초과로 이관됐다. 정상 실행 #305에서 검색은 약 1,889ms였다. 단계별 임베딩·네트워크·검색 시간은 없으므로 초과 원인은 미확인이다. 안전 이관은 관찰됐지만 정상 질문의 응답을 제공하지 못했다.
2. **F-S1-03:** PR #31에서 지식의 내부 출처 표현을 정리하고 main `eb747df`에 병합했다. R02 답변 생성 규칙 수정은 별도다. VM에 해당 지식이 적용·재색인되고 최종 답변이 재시험되기 전까지 해결로 기록하지 않는다. 마지막으로 확인한 VM 상태는 이전 색인이다. 현 시점은 R01 인계를 통해 재확인한다.
3. **설계서 체크:** 청킹 단위·오버랩·길이, 모델·차원, 코사인·인덱스·메타데이터, 백업·복구·확장 방안은 공식 [RAG 설계서](../project/RAG-ARCHITECTURE.md)와 [제출용 요약](rag-architecture.md)에 작성돼 있다. 작성 완료와 VM 재시작 복구, pgvector 전환, 운영 백업 시험 완료는 다르다.
4. **WF-01 결과 표기 확인:** R05 결과서의 개별 3회는 `FAIL/PASS/FAIL`이지만 일부 설명은 `2/3`이라고 표기한다. 대상 실행과 판정 기준이 다른지 R05 확인 전 수치를 합치거나 기대값을 수정하지 않는다. 세 번째 응답은 번호를 안내했으나 기대 단어와 표현이 달랐다고 기록돼 있다.

## 공용 환경과 보안

- R01의 최신 마무리 방향과 R05의 시험 일정을 확인하고 공유 VM 작업 창을 조율한다. 실제 VM의 색인·검색 원본과 지식·Credential 연결을 보존한 뒤 [PR #31 재색인·원복 계획](p31-vm-index-recovery-plan.md)을 따른다. 이전 메모리 색인은 즉시 복원되지 않으며 이전 색인본 전체 재실행과 검증이 필요하다.
- R05가 n8n 실행 기록의 B01 헤더에 팀 키가 남는 문제를 보고했다. 원시 실행 기록·캡처·키를 공개 저장소나 채팅에 올리지 않는다. 키 교체·저장/접근 정책 판단은 R01·R02의 후속 조치다.
- R05의 25개 사례 3회 반복 결과는 당시 시험 범위이며 전체 고장·조회·복구 시험이 아니다. 기존 실패와 미실행을 보존하고 새 결과는 별도 실행묶음으로 기록한다.

## 개선 관점

- **강점:** 실제 안내·가상 정책 구분, 문서와 절 단위 근거, 공개/제한 검색 분리, 미준비 색인의 안전 차단, 팀 간 단일 검색 결과 계약.
- **한계:** 3초 제한 대비 지연 변동, 실제·가상 지식의 최신성 승인 필요, 내부 호출자의 권한 신뢰, 메모리 재시작·재색인, 동시성·롤백 미검증, 본문 출처 메모가 시민 답변에 섞일 가능성.
- **후속:** 대표 질문 근거와 답변의 문장별 정확성, 시민·담당자 양성 대조, 관측 가능한 지연 계측, R05 공식 재판정. PostgreSQL·pgvector는 상태 DB와 구분한 향후 검토다.

## 2026-11-07 독립 로컬 확인

- workflow 정적 테스트 4/4, 시민·담당자 모의 어휘 검색 2/2, 청킹·권한 경로·두 제한 문서 canary 검사 7/7이 통과했다. 명령은 각각 `python -m unittest discover -s scripts/test -p 'test_n8n_rag*.py' -v`, `python -m unittest discover -s scripts/test -p 'test_rag_local_evaluation.py' -v`, `python -m unittest discover -s scripts/test -p 'test_prepare_rag_chunks.py' -v`다. 인증 HTTP 7개는 키 없이 실행하여 모두 생략됐다. 모의 결과는 실제 서버 사용자 인가나 VM 검색 성능을 입증하지 않는다.
- 로컬 n8n healthz 응답은 확인됐으나 검색 Credential·색인 상태를 확인하지 못해 실제 임베딩 호출이나 반복 지연 측정은 실행하지 않았다. 관련 키를 기록하거나 기존 실행 환경을 수정하지 않았다.
- 시민 검색 경로는 readiness 읽기 → public 검색 → readiness 재확인으로, 세 load 노드가 Embeddings에 연결된다. [n8n 2.42.6 load 구현](https://github.com/n8n-io/n8n/blob/n8n%402.42.6/packages/%40n8n/ai-utilities/src/utils/vector-store/createVectorStoreNode/operations/loadOperation.ts)은 load마다 `embedQuery`를 호출한다. 이는 추가 계측할 후보일 뿐 실행 #796 지연의 원인으로 확인된 것은 아니다.
- PR #31을 색인한 독립 로컬 n8n의 실제 모델 비교에서 R02는 기존·수정 support 각각 자동답변 15/15, 내부 출처 표현 0/15, QR 절 인용·5자리 표현 15/15라고 보고했다. [R02 결과](https://github.com/ik-e/dubakwi-ttareungi-support/pull/31#issuecomment-6681297214). 이는 로컬 결과이며 VM 재색인·R05 공식 재판정은 아니다.

## R01 인계: 로컬 검색 시간 측정 도구

- `scripts/dev/rag_latency_probe.py`는 **로컬 루프백 검색 API만** 대상으로 합성 질문을 반복 호출하고 전체 응답시간·상태·제한 문서 표시 여부만 요약한다. 키·원문 질문·응답 본문은 출력하지 않으며 리다이렉트와 외부 URL을 거절한다. 외부에 보내는 본체·Jira 호출은 하지 않는다.
- 별도 개발 n8n에서 workflow 게시·색인과 내부 인증이 이미 준비된 경우, 키를 비공개 환경 변수 `DUBAKWI_INTERNAL_KEY`에 설정한 다음 `python scripts/dev/rag_latency_probe.py --iterations 3`으로 실행한다. 임베딩 API 비용이 발생할 수 있다. 공용 VM에 적용하는 도구가 아니다.
- 모의 HTTP 서버 시험 4개로 로컬 제한·리다이렉트 거절·비밀 비출력·제한 문서 감지를 검증했다. 실제 임베딩 요청과 지연은 실행하지 않았다. 결과는 검색 직접 호출의 전체 시간이며 단계별 원인, 사용자 인가 종단이나 R05 공식 판정은 별도 확인해야 한다. 응답 오류 등으로 검사가 불가능하면 비노출을 확인한 것으로 간주하지 않는다.
