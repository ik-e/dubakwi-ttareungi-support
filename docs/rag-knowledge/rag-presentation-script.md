# 두바퀴 RAG 발표 자료와 대본

발표 목적: 따릉이 상담 자료가 검색 가능한 형태가 되기까지 설명. 기준: 2026-11-05 v0.2, 교육용 로컬 구현 및 VM 수동 색인·검색 부분 시험. 실제 서버 사용자 인가·VM 재시작/재색인·공식 사례 판정은 미완료. R01이 [VM 실행 기록](../../runs/public/20261105-111311-vm-rag-integration/report.md)에 맞춰 상태 문구를 동기화했으며 새 실행은 하지 않았다.

## 슬라이드 1. RAG가 필요한 이유

**화면에 넣을 내용**

- 시민 질문: “따릉이 대여가 안 돼요.”
- 관련 문서를 찾고, 찾은 내용을 답변 근거로 사용
- 데이터 수집 → 전처리 → 청킹 → 임베딩 → 저장·검색

**발표 대본**

> 안녕하세요. 두바퀴 RAG 담당 장상옥입니다. RAG는 질문을 받았을 때 관련 자료를 먼저 찾고, 그 내용을 근거로 답변하도록 돕는 방식입니다. 저희는 따릉이 상담 자료를 어떻게 모으고, 검색할 수 있도록 바꿨는지 다섯 단계로 설명드리겠습니다.

## 슬라이드 2. 데이터 수집

**화면에 넣을 내용**

- 따릉이 앱 챗봇의 대여·반납·요금·고장 안내
- 따릉이와 서울시·서울시설공단 공개 자료
- 시민용 문서 6개 + 교육용 담당자 정책 2개 = Markdown 8개
- 담당자 이관·티켓 처리 문서는 **가상 정책**

**발표 대본**

> 먼저 제가 따릉이 앱 챗봇에서 안내를 직접 수집했고, 따릉이와 서울시의 공개 자료도 참고했습니다. 시민에게 필요한 문서 여섯 개와 담당자용 문서 두 개를 준비했습니다. 담당자용 문서는 실제 따릉이 내부 규정이 아니라 프로젝트 시연을 위한 가상 정책입니다.

## 슬라이드 3. 전처리

**화면에 넣을 내용**

- 주제별 Markdown 문서로 정리
- `[실제 안내]` / `[가상 설정]` 구분
- 출처·확인일·문서 버전·권한 기록
- 파일 해시와 승인 상태 확인

**발표 대본**

> 수집한 내용은 대여, 반납, 요금처럼 주제별 문서로 다시 정리했습니다. 실제 안내와 가상 설정은 구분하고, 출처와 확인 시점을 기록했습니다. 또한 문서가 바뀌었는지 확인하는 해시와 승인 상태를 관리합니다. 현재 자료는 승인 전이라 교육용 시연으로만 색인했습니다.

## 슬라이드 4. 청킹

**화면에 넣을 내용**

| 항목 | 현재 값 |
| --- | --- |
| 분할 기준 | Markdown 절 제목과 문단 |
| 청크 수 | 44개: 시민용 36개, 담당자용 8개 |
| 글자 수 | 최소 61자 / 중앙값 124.5자 / 최대 251자 |
| 오버랩 | 전처리 청크 기준 0자 |

- 절 전체로 묶는 구조 비교: 41개, 61 / 123 / 364자
- 두 방식의 검색 정확도 비교는 미실행

**발표 대본**

> 문서를 통째로 검색하면 관련 없는 내용도 함께 전달될 수 있어 작은 조각으로 나눴습니다. 저희는 Markdown의 절 제목과 문단을 기준으로 나누고 실제 안내와 가상 설정이 섞이지 않도록 처리했습니다. 현재 전처리 결과는 44개이며 길이는 최소 61자, 중앙값 124.5자, 최대 251자입니다. 이 수치는 토큰이 아니라 글자 수입니다. 절 전체로 묶는 구조와 길이는 비교했지만, 두 방식의 검색 정확도 비교는 아직 하지 않았습니다.

## 슬라이드 5. 임베딩과 검색

**화면에 넣을 내용**

- 모델: OpenAI `text-embedding-3-large`
- 로컬 실행 벡터 한 개에서 **3,072차원 확인**
- 질문과 문서의 벡터를 **코사인 유사도**로 비교
- 예: “대여가 안 돼요” → `rental-guide / 연결과 대여 실패`

**발표 대본**

> 나눈 청크는 OpenAI의 text-embedding-3-large 모델로 숫자 벡터로 바꿨습니다. 로컬 실행 결과에서 벡터 한 개의 길이는 3,072차원이었습니다. 질문도 같은 방식으로 바꾸고, 벡터 사이의 코사인 유사도를 비교해 관련 내용을 찾습니다. 예를 들어 대여가 안 된다는 질문에서 대여 실패 안내 절이 검색되는 방식입니다.

## 슬라이드 6. 저장·권한·복구

**화면에 넣을 내용**

- 현재 로컬: n8n Simple Vector Store, 메모리 기반
- `public`과 `restricted` 저장 공간 분리
- 재시작 시 재색인 필요 → 준비 전 검색 차단
- 향후 계획: 팀 VM의 Docker 기반 PostgreSQL + pgvector 검토
- VM 원본 수동 색인44청크·같은 서버 검색 확인, 실제 사용자 권한 연결·재시작 복구는 미완료

**발표 대본**

> 현재 로컬에서는 n8n의 메모리 기반 벡터 저장소를 사용합니다. 시민용과 담당자용 저장 공간을 나눠 검색 전에 접근 범위를 선택했습니다. 다만 현재 확인한 것은 모의 권한 시험이며 실제 서버 사용자 확인과의 연결은 남아 있습니다. 메모리는 재시작하면 사라질 수 있어 재색인이 필요하고, 앞으로는 팀 VM의 Docker 기반 PostgreSQL에 저장하는 방향으로 준비하고 있습니다. pgvector 연동은 아직 검증 전입니다.

## 슬라이드 7. 현재 결과와 다음 단계

**화면에 넣을 내용**

- 교육용 질문 Q01~Q13: 기대 문서·절 상위 3개 포함 각 13/13
- WF03 해외 이용 질문: `empty`
- 기대 절이 2위인 질문도 있어 최종 답변 품질 확인 필요
- VM 추가 확인: 원본 수동 색인44청크·실제 검색 HTTP7메서드. 전체 공통 통과율과 구분
- 다음: 서버 사용자 권한 연동·VM 재시작/재색인·R05 공식 시험

**발표 대본**

> 로컬 교육용 질문 열세 개에서는 기대 문서와 절이 상위 세 결과 안에 포함됐고, 해외 이용 질문은 검색 결과 없음으로 반환됐습니다. 이후 팀 VM에서 원본 수동 색인44청크와 같은 서버의 검색을 확인했습니다. 이 숫자들은 최종 답변 정확도나 공통 전체 통과율이 아닙니다. 앞으로 실제 사용자 권한 연결, VM 재시작·재색인과 R05 공식 시험을 진행하겠습니다.

## 발표 중 주의할 표현

- 로컬44개 전처리 결과와 VM 원본 Manual의44개 삽입 성공을 구분해 말한다. 전체 저장 벡터 덤프·비용·재시작 복구까지 확인한 것으로 확대하지 않는다.
- 13/13은 선택된 교육용 질문의 기대 문서·절 포함 수다. 전체 공식 사례 통과나 서비스 정확도로 표현하지 않는다.
- 3,072차원은 로컬 벡터 한 개의 실측이다. PostgreSQL+pgvector는 향후 계획이며 VM 동작을 증명하지 않는다.
- 상세 수치와 출처·한계는 [템플릿 기반 설계서](rag-architecture.md)와 [RAG 상세 설계](../project/RAG-ARCHITECTURE.md)를 참조한다.
