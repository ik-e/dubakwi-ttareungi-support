# RAG 권한 전달 통합 시험 준비

작성: 2026-11-05 · 담당: R03 · 상태: **시험 계획, 종단 시험 미실행**

## 목적과 현재 상태

사용자 조회 → R02 B05 검증 → P19 B13/B14 → RAG 검색에서 권한이 유지되는지 확인한다. 로컬에서 내부 호출에 모의 권한을 넣은 검색 시험과, VM P11·RAG의 별도 부분 시험은 있었지만 이 전체 경로의 시민·담당자 종단 시험은 아니다.

현재 VM의 과정용 data-api는 `{name, dept}`를 공급하고 B05는 이를 citizen/public으로 처리한다. 팀 형식 `{id, role, access_levels}`의 담당자 사례를 실행하려면 R04의 팀 모의 사용자 공급 및 R02 P19 연결이 필요하다. 부서명이나 질문 속 자기소개만으로 restricted를 주지 않는다.

## 공통 준비

1. R01이 준비한 시험 환경과 배포 커밋, P19 및 검색 JSON 해시, n8n 버전, 검색 주소와 실행 기록 접근을 확인한다. 실제 주소·키는 비공개로 전달하고 공개 기록에는 남기지 않는다.
2. R02의 B01에는 시민 입구 `X-Team-Key`, B14에는 내부용 `X-Internal-Key`가 각각 올바른 Credential로 연결됐는지 확인한다. 검색 Webhook과 내부 키는 시민에게 직접 제공하지 않는다.
3. 교육용 지식의 승인 상태와 색인 완료 및 public/restricted 검색 준비를 확인한다. 제한 문서 양성 사례는 해당 문서를 찾을 수 있는 질의를 이용한다.
4. R04가 제공한 테스트 사용자와 응답 형식, 미등록 및 조회 실패의 안전한 시험 방법을 확인한다. 실제 개인정보를 쓰지 않는다. 담당자 public-only 조합과 오류 주입이 없으면 해당 사례는 blocked로 남긴다.
5. R05와 시험 실행 ID, 요청 및 근거·실행 노드 증거의 가림 방법, 공식 사례와 로컬 참고 시험을 구분한다. 상태·Jira가 mock이면 명시한다.

## 기록·판정

- 각 사례에 실행 시각, 배포 커밋과 워크플로 해시, 사용자 식별자(모의 값), 조회 응답 형태, B05 역할·권한, B14 실행 여부 및 전달 권한, 검색 상태·문서 ID·접근 수준, restricted/canary 노출 여부를 기록한다.
- 검색·최종 응답에 제한 본문·ID·출처·canary가 하나라도 시민에게 노출되면 실패다. 문의 소유권은 RAG 문서 접근과 별도로 시험한다.
- 조회 거절 사례는 HTTP 코드뿐 아니라 B14 검색 노드 미실행을 n8n 실행 기록으로 확인한다.
- 각 사례는 pass/fail/blocked/not_run을 구분하고, R05 공식 판정 전에는 R03 참고 시험으로 표시한다. 실제 인가 보안 승인으로 확대하지 않는다.
- 토큰, 내부 인증값, 실제 식별정보와 원문 실행 로그는 공개 파일에 저장하지 않는다. 공개 기록에는 가린 집계·근거 위치만 남긴다.

## 실행 준비 현황과 우선순위 (2026-11-05)

- **정적 준비 확인:** `data/users.json`의 시민 3명·담당자 2명 권한과 미등록 ID 부재를 6/6으로 확인했다. [가린 정적 확인](../../runs/public/20261105-141845-local-rag-permission-fixture-review/summary.json). 서버 조회나 권한 종단 시험 결과가 아니다.
- **기존 VM 부분 근거:** [PR #21 기록](../../runs/public/20261105-114531-vm-course79-data-api/summary.json)의 과정 data-api/P11, [PR #22 기록](../../runs/public/20261105-121200-vm-p19-connection/summary.json)의 public fixture 문맥 B14 검색은 별도 부분 시험이다. B05부터 RAG까지 실제 사용자 권한을 연결한 시험은 아니다.
- **실행 순서:** R05·R02·R04의 공식 입구 사례가 먼저다. R01/R04가 팀 사용자 공급과 실제 저장 연결 순서를 확정한 뒤 R02의 P19 배포 범위 및 R05의 공식 판정 도구에 맞춰 이 표를 실행한다. 입구 사례에 이 계획의 정적 결과를 합격으로 넣지 않는다.
- **차단 조건:** 현재 fixture에 담당자 public-only 계정이 없고 조회 장애 주입 방법도 확인되지 않았다. 별도 승인된 시험 데이터·격리된 고장 경로가 준비되기 전 AUTH-03/05는 blocked다. 기존 VM 사용자·데이터나 운영 상태를 임의로 바꾸지 않는다.

## R04 팀 사용자 API 검토 (PR #26, 2026-11-05)

- PR #26 검토 기준 커밋 `dd1f406643eddc5784137820ce57a488a7019ec1`. `/employees/{user}`는 내부 `X-Internal-Key` 인증 후 `{id, role, access_levels}`만 반환하므로 P19 B05의 팀 형식과 필드 계약이 맞는다. 독립 임시 사본에서 API 테스트 7/7 통과. 이 시험은 API 자체의 로컬 실행이며 VM 배포·B05→RAG 종단 결과는 아니다.
- R02 P19 브랜치 검토 당시 `dc6eb8e`의 B04는 여전히 `data-api:8800`을 사용하고 내부 인증이 없다. 팀 API를 사용할 때 `dubakwi-user-api:8801`과 `X-Internal-Key` Credential을 연결하고 신원 조회의 401·404·네트워크 오류 처리 및 역할 전달을 시험해야 한다. 상세 계정 및 Credential 값은 공개 기록에 남기지 않는다.
- 서버 `log_message`는 URL 경로를 그대로 출력해 `/employees/<사용자 ID>` 및 `/records/<티켓 ID>`가 로그에 남는다. 주석의 비식별 처리 의도와 다르므로 R04에 경로의 식별자 가림 또는 고정 경로 템플릿 기록을 요청한다. 테스트 및 로그에 실제 개인정보가 들어가지 않게 한다.
- 검색의 시민 restricted 비노출은 기존 내부 모의 요청에서 확인했지만, 팀 사용자 API→B05→B14→RAG 실제 전달은 서버 배포·P19 연결 전이므로 미실행이다. public-only 담당자 및 조회 장애 사례의 안전한 시험 방법도 필요하다.
- 기록 조회 API의 `requester`는 내부 인증된 호출자가 제공한다. 신뢰할 수 있는 서버 확인 ID를 전달하는지 본체 연결에서 함께 확인하며, 문서 검색 권한과 기록 소유권을 별도로 검증한다.
