# 전체 설계 차이 수정·검증 계획

- 버전: v1.1 / 2026-11-06 KST / R01 / P09~P31 중 대조표의 잔여 작업
- 기준: [64개 설계·구현 대조표](design-implementation-mapping.md), [J01~J03 공통 기준](parallel-integration-contract-v1.md), [팀 헌장](../docs/project/TEAM-CHARTER.md).
- 범위: **기존 대조표 64개 모두를 작업·완료 시험·증거에 연결한다. 전체 설계의 모든 문장을 완전 증명하거나 기능 구현·실연동을 완료한 문서는 아니다.** 이후 발견한 요구·결함도 같은 원장에 추가한다.
- 상태: R01 수정 기준안 작성. 생산·소비 역할·R05의 영향 검토는 대기다. 승인받은 것으로 간주하지 않으며 업무 JSON·VM·기존 데이터는 변경하지 않는다.
- 항목별 작업·원래 미완료 조건·예정 시험·증거·막힘은 [64개 실행 매핑](contracts/full-system-coverage.json)이 원본이다. 기존 대조표는 당시 증거를 보존하며 현재 작업 상태는 개발 계획에서 관리한다.

## 1. 빠뜨리지 않는 기준

각 대조 ID는 주 작업 묶음 하나, 의존 묶음, 보완 행동, 기존 완료 조건, 예정 시험 ID, 생산/소비 검토, 필요한 실제 효과 증거를 갖는다. 상태는 계획과 결과를 분리한다. `planned`인 시험을 실제 실행 가능한 runner나 통과로 세지 않는다. 아래 AC-*는 R05가 정식 cases에 연결하거나 추가할 **인수 시험 식별자**이며 기존 WF/TC 번호를 재정의하지 않는다.

원래 완료 조건을 삭제하거나 구현 결과에 맞춰 낮추지 않는다. `blocked_dependency`도 커버되지만 해결된 것은 아니다. 설계 범위의 미구현 S10은 별도 한계로 남기며 자동 재개 기능을 새로 추가하지 않는다. 64/64 연결 수치는 통과율이 아니다.

## 3. 미정이었던 Jira 문맥 공통 형식 — D01 기준안

R01 조회 provider와 R04 state/handoff가 같은 문맥을 읽도록 **기존 Jira 이슈의 서비스 작성 댓글에 가린 스냅샷**을 둔다. 새 서버·전체 상담 이력 DB를 만들지 않는다. [모의 스냅샷](contracts/jira-case-context-v1.example.json)을 생산·소비 공통 입력으로 사용한다. 기존 자유문장 댓글은 자동으로 신뢰 가능한 스냅샷으로 간주하지 않는다.

| 항목 | 고정 규칙 |
| --- | --- |
| 텍스트 형식 | 첫 줄 `[dubakwi-case-context:v1]`, 다음 줄에 JSON 객체 한 개. JSON 내부 개행은 escape한다. Jira API v2 문자열 댓글의 body를 기준으로 하며 ADF 사용 시 소유자가 동일 텍스트 추출을 제공한다 |
| 필드 | schema_version=1, scope, case_id, owner_id, first_request_id, ticket_key, request_id, event_id, revision, phase, support, facts. support는 공통 SupportCase이며 version=null. revision은 내부 context_revision으로만 사용 |
| phase | wait/handoff/followup/close/save. 같은 요청의 초동 이관 후 보충 문맥은 별도 followup 이벤트로 구분 |
| 이벤트 ID | UTF-8 `JSON.stringify([scope, case_id, request_id, phase])`의 SHA-256 소문자 hex. 첫 요청 ID·actor·key는 별도로 연결 검증 |
| 작성 주체 | 비공개 설정의 서비스 Jira accountId 허용목록과 댓글 author.accountId 대조. 시민 문자열이나 댓글 본문의 author 주장은 신뢰하지 않음 |
| 연결 | 현재 DB의 scope/case/owner/first_request/known Jira key와 기존 label·이슈 연결을 모두 대조. 요청자가 넣은 소유권이나 key만으로 읽기 성공하지 않음 |
| 최신 선택 | 모든 댓글 페이지를 절대 마감 안에서 읽고 DB latest_completed_request_id에 해당하는 유효 문맥의 revision 최대값으로 복원한다. 최종 save는 현재 요청의 유효 문맥을 별도로 확인한다. 같은 revision/event의 동일 payload 재전송은 한 번으로 보며 다른 payload·버전·상충 revision은 읽기 실패. 댓글 시간만으로 최신 선택하지 않음 |
| 쓰기 | 기존 case 단독 처리권 아래 직전 검증 revision+1. prepare/bind 이후 쓰며 성공 응답과 재조회 일치 후 context_saved 확인. 응답 유실 시 event_id로 먼저 조회하고 맹목적 추가 댓글/업무 재호출0 |
| 저장 의미 | 스냅샷의 handed_off는 업무 문맥이며 배정·알림 성공의 단독 증거가 아님. 현재 담당·시도/성공 표식·실제 Jira 상태를 별도로 확인한 뒤 save/finish |
| 가림 | facts만 최소 저장. 전체 대화·전화/메일 원문·Credential·실제 Discord ID는 저장0. confirmed는 허용 원본 증거가 있는 사실만 |
| 부재/불완전 | 본인 여부 미확인 시 내용 반환0. 본인 연결은 있으나 문맥이 없거나 검증 실패하면 begin은 기존 state_error, records는503/lookup_error. 빈 facts·waiting_info·denied 성공으로 대체0 |
| 기존 시험 건 | 예전 댓글의 상태/사실을 추정 이관하지 않음. 별도 읽기 전용 증거로 보존하고 새 namespace부터 검증. 기존 건 전환은 원소유/작성근거를 확인한 별도 인계로만 진행 |

scope를 댓글에 저장하는 것은 업무 namespace 식별이며 비밀 키가 아니다. 이 규칙은 데이터 무결성 기준이며 Jira 관리자에 대한 암호학적 위조 방지를 주장하지 않는다. 서비스 계정 공유·권한을 포함한 위협 범위는 운영 manifest에 명시한다. 실제 Jira API의 크기 제한·페이지 처리·UTF-8/ADF 왕복·다중 댓글/응답 유실 시험은 AC-J03/AC-J15에 포함하며 측정 전 지원 크기를 보장하지 않는다.

D01의 검토 결과는 R04(쓰기/복원)·R01(조회/환경)·R02(소비)·R05가 한 번 확인한다. 구조 fixture만으로 배포 승인하지 않는다. 상세 설계의 원본 반영은 각 소유자가 같은 구현 검토 단위에 포함한다.

## 4. 이관 뒤 새 위험 — D02 기준안

같은 사건에 추가 위험 진술이 들어오면 기존 handed_off·ticket·역할·우선순위·보완 횟수를 유지한다. 새 진술은 reported/uncertainties에 보존하고 허용된 public 근거가 있으면 초동 안내를 덧붙인다. 새 담당 지정·재알림·종료·새 티켓 생성은 하지 않는다. 이번 문의의 문맥 저장과 기존 효과 확인 후에만 save한다.

시민 Response의 기존 route `담당자 이관`, reason `needs_human`을 사용하고 ‘기존 문의에 추가 내용을 전달했습니다. 새로운 위험 내용은 담당자 확인이 필요합니다.’로 안내한다. 최초 이관을 새로 성공시켰다거나 긴급 재알림했다고 말하지 않는다. 초동 근거가 없으면 임의 안전 지침을 만들지 않는다. 문맥·이전 효과 검증 실패는 기존 partial_effect/확인 필요 경로이며 성공 문구를 내보내지 않는다.

이는 **추가 위험의 기록·기존 담당자 확인까지** 지원한다는 제한이다. 자동 긴급 재배정/재알림을 지원하지 않는 한계를 공식 결과·시연에 명시한다. 다른 사건은 별도 문의로 접수하는 기존 정책을 안내하며 기존 실패 요청을 우회 재실행하지 않는다. 새로운 에스컬레이션 기능이 필요하면 별도 범위 변경으로 취급한다. R02·R04·R05 영향 검토 및 AC-B07/AC-J02 후에만 활성화한다.

## 6. R05에게 필요한 시험 준비물

R02는 정상·LLM/단계시한 사본과 버전, R04는 Jira/state/DLQ 고장 사본·담당별 읽기 fixture, R03은 지식/색인/검색 버전·권한별 canary, R01은 묶음별 scope/경로/비공개 설정/백업/시험 창을 제공한다. 시험 대상은 citizen-a/b 소유의 **새 검증 문의 각1건**, 타인·미존재 키, waiting_info/handed_off/직원 종료 건이다. 실제 key는 비공개 대응표로만 연결한다.

R05는 모든 AC 행을 기존 WF/TC 또는 새 사례에 연결하고 입력·기대값·fault 설정/해제·부작용 관측 지점을 정의한다. 정상, failure_handling, recovery를 분리하고 응답 충족과 실제 Jira/state/DLQ/알림 충족도 나눠 판정한다. TC12·F-S1-03·TC14는 수정본 배포/재시험 전 미해결이며 기존 실패 기록을 보존한다.

특히 조회는 target 이슈 쓰기0, 재전송은 LLM/생성/배정/알림0, 후속 문맥 갱신은 동일 티켓1건·횟수/역할/상태 유지, 장애는 known ID·원실행·DLQ·재전송 차단까지 본다. 실제 알림 API 수락과 메일 수신/담당 열람을 혼동하지 않는다. 로그의 민감값 검사는 본문뿐 아니라 sources/Jira/알림/실행 로그/Discord 전체를 대상으로 한다.

## 7. 완료를 선언하는 순서

1. R01: 64개 계획 연결 검사, D01~07 영향 검토 취합. 각 담당은 fixture로 개발 착수하고 승인/부재를 구분한다.
2. 기능 소유자: 수정·상세 설계·경계별 로컬 시험·미실행·렌더/원복 결과 인계. 구체적인 파일/노드 인계를 기록하고 공용 VM은 편집하지 않는다.
3. R01: 검토된 main 버전·이미지·코드/설정/사본을 manifest로 고정. R05 실행 종료 후 백업→사전 비교→새SQL/서비스→state/handoff→support→검색/재색인→봇 순서로 검증하며 기능 호환 묶음은 함께 활성화한다. 고장은 끝까지 시험 사본에만 적용한다.
4. R05: 각 AC의 실제 효과를 원본 결과와 연결. 실패 후 새 실행묶음 재시험, 해제 실패는 중단. W10 격리 복원과 W11 운영 한계도 포함한다.
5. R01: 64개 각각을 verified/failed/unverified/blocked/not_implemented로 판정 근거와 함께 취합한다. required 행에 failed/unverified/blocked가 있으면 마감 차단. S10은 재개 드라이버만 not_implemented이며 AC-S10의 수동 확인·재전송 차단·한계 표시는 여전히 필수다. 미구현 한계를 수용하더라도 ‘자동 복구 포함 전체 설계 완료’는 선언하지 않는다. 결과서·발표·PR은 동일 버전·제한을 사용한다.

새 결함/누락 발견 시 대조표와 coverage에 새 ID를 추가하고 계획 버전을 올린다. 아래 검사는 알려진 64개에 빠진 계획이 없는지만 보장하며 미래 결함이 없음을 보장하지 않는다.

계획 연결은 [로컬 검사 결과](../runs/public/20261106-234737-local-full-system-coverage/report.md)에서 64/64 연결·순환0·의도적 오류8개 검출을 확인했다. 실제 인수 시험을 실행한 결과는 아니다.
