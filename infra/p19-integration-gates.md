# P19 실제 연결 전 R01 확인

- 버전 v0.1 / 2026-11-05 KST. P12/P19, R01 통합 검토.
- 고정: support `5e0026c`, 문서 후속 `6afb94d`, state/DLQ/handoff `168c79c`, errors `ff19178`.
- [검토·VM 읽기 증거](../runs/public/20261105-201053-mixed-p19-integration-gates/report.md). 현재 판정은 **#27 수정 대기, #16 통합·게시 보류**다. VM 설정·DB·업무 데이터를 변경하지 않았다.

## 1 병합 순서와 확인 결과

순서는 #27 → #16이다. #27의 수정본에 대한 경계/관련 기능 시험과 영향 역할 검토가 먼저다. `MERGEABLE`은 Git 충돌 여부이며 기능 승인이 아니다. #27에는 기존 CHANGES_REQUESTED 검토가 남아 있다.

`168c79c`와 `5e0026c`의 별도 작업본 병합 예행에서 `docs/project/WORKFLOW-DESIGN.md`의 내용 충돌을 재현했다. 예행은 abort했고 기존 역할 브랜치는 변경하지 않았다. #27 병합 후 R02가 main을 반영하고 양쪽 계약·검증 이력·미완료 항목을 보존해 충돌을 해결한다. support 코드가 고정 버전과 같은지 Git blob SHA-256으로 확인하고, 달라졌다면 새 버전을 고정해 시험한다.

`6afb94d`는 문서3개만 변경했고 support는 `5e0026c`와 바이트 동일하다. 원본 Git blob SHA-256은 `b44fb305cfb20f7def0613185b710a5e6d6a228b884bdff40a075c94cef36ada`다. 환경 치환·JSON 재직렬화한 배포 사본의 해시와 구분한다.

## 2 병합 전 R04 수정 경계

H23은 `first_request_id`의 특수문자를 `_`로 바꾸고 scope·소유자를 포함하지 않는다. `req.a`·`req/a`, 다른 scope/소유자가 모두 `dubakwi-req_a`를 만든다. H24의 label 검색 경로는 검색 결과가 여러 건이어도 첫 이슈를 검증 없이 재사용한다. 합성 두 이슈 입력에서 첫 이슈를 reused/confirmed로 반환함을 재현했다. 실제 Jira는 호출하지 않았다.

R04는 생성·검색·키 재사용·save가 같은 충돌 방지 식별/문의·소유권 검증을 사용하도록 수정하고, 서로 다른 요청·scope·소유자·복수 검색 결과의 회귀를 제공해야 한다. R01이 R04 업무 Code를 대리 수정하거나 기존 검토를 승인으로 바꾸지 않았다.

한도 이관 뒤 같은 case의 새 요청에서 재배정·재알림이 반복되는 결함은 별도 추적한다. 같은 요청의 재시도 중 알림 중복과 동일 원인이라고 단정하지 않는다. 각각 request_id·case_ref·transition_key와 배정/알림 호출 수로 판정한다.

## 3 VM 읽기 대조

사용자가 기존 웹 SSH에 로그인한 뒤 Docker 목록·n8n SQLite 읽기 전용 조회·서비스 DB SELECT·환경변수 이름 존재 여부·health만 확인했다. 기존 Python 이미지의 임시 조회 컨테이너는 network none/read_only, n8n 볼륨 readonly로 사용했다. 기존 서비스 재시작·권한 변경·비밀 출력·Credential 등록은 없다.

- 기준 state는20노드, DLQ는6노드다. 이름에 state/dlq를 포함한 기존 사본을 모두 대조했으며 동일 구성/연결선인 사본은 없었다. state의11노드 사본과 DLQ의5노드 사본도 최신 원본과 다르다. mock 사본도 포함돼 있으므로 이름만으로 최신본을 선택하면 안 된다.
- `dubakwi_service` 함수 조회 결과는 `dlq_apply`, `state_apply`, `state_ref_json`뿐이다. `005` 사례 함수는 없으므로 `005~006` 적용 완료로 기록할 수 없다. 권한 적용은 재조회하지 않았다.
- 기존 n8n 환경에 `DUBAKWI_SCOPE`가 없다. 상태 조회 시 n8n 실행 중이고 health200이다.

## 4 수정 후 적용 게이트

1. R04 수정 커밋과 관련 회귀·R02/R05 계약 검토를 취합해 #27을 병합한다. R02가 #16 충돌을 정리하고 새 시험 버전을 고정한다.
2. 검토된 main의 원본·현재 DB/복제본 상태를 다시 대조한다. 별도 검증 DB의 `005~006` 검사 결과를 검토하고, 서비스 DB 변경 전 백업·적용 대상/owner/runtime·기존 업무 행 보존을 확인한다. 이번 점검은 SQL 적용 허가나 적용 완료 증거가 아니다.
3. service DB에 검토된 `005~006`을 적용할 때 함수·runtime 권한을 확인하고, 최신 state/DLQ 사본을 환경 ID/Credential만 연결해 비활성 반입한다. Jira 설정·역할별 담당 매핑은 R04와 확인한다.
4. R02 support와 errors의 scope를 같게 연결할 방식을 확정한다. `DUBAKWI_SCOPE`가 없는 상태를 준비 완료로 취급하거나 시험을 위해 n8n을 임의 재시작하지 않는다. 재시작이 필요하면 RAG 재색인·진행 실행 영향도 함께 계획한다.
5. state/DLQ/handoff/errors의 원본 커밋/해시와 승인된 환경 치환을 검토한 뒤 사본만 게시한다. 운영 P11은 유지한다. 실제 S1의 Jira 생성1·종료·DB completed·최종 응답·DLQ0과 재전송 시 추가 효과0을 새 실행 증거로 남긴다.

키를 새로 공유할 필요 없이 R01이 기존 비공개 키로 실행한 뒤 실행 ID·가린 결과를 인계할 수 있다. R02가 직접 호출하려면 기존 승인된 비공개 전달 경로를 사용하고 공개 PR/문서에 키를 넣지 않는다.
