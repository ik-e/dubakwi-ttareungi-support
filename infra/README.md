## 2 최초 준비와 배포 순서

기존 VM은 [배포 전 점검](vm-preflight.md)을 먼저 따른다. 아래 compose 작성/기동은 향후 검토된 교체/확장 구성이 있을 때의 절차다. 현재 infra/compose.yaml이 없으므로 아래 up 명령을 실행하거나 같은 포트에 두 번째 n8n을 만들지 않는다.

1. R01이 확정 접두사 dubakwi 적용·VM 자원·Docker Compose 사용 가능 여부·접속 URL/TLS·외부 포트·볼륨·백업 위치를 확인한다. R04는 Jira 및 저장 경계를 확인한다(D01/D03).
2. R01이 실제 이미지 버전과 compose를 작성하고 R04가 영속성·DB 격리·비밀 주입을 검토한다. 외부 공개는 필요한 입구로 제한하고 내부 DB·관리 연결을 무조건 공개하지 않는다.
3. R01이 설정 예시를 작성하고 환경별 실제 값을 서버에 주입한다. n8n Credential·암호화 키 복구 방식도 확인한다. Discord 봇 토큰과 내부 Webhook 키는 환경 비밀로 주입하고 사용자/서버 ID 매핑도 공개 데이터에 넣지 않는다. Gateway 기본안에서는 Discord Interactions HTTP 입구를 별도로 공개하지 않는다. 설정 확장 결과가 비밀을 포함할 수 있으므로 출력 전체를 보고서에 붙이지 않는다.
4. compose 작성 후 저장소 루트에서 `docker compose -f infra/compose.yaml config --quiet`로 구성 문법을 확인하고, `docker compose -f infra/compose.yaml up -d`로 실행한다. 두 명령은 해당 파일·환경 준비 후에만 유효하다.
5. R01이 하위 워크플로우·Credential·환경별 ID·Error Workflow 지정을 확인한다. R03이 지식/색인 준비와 활성 버전을 확인한다. DB 마이그레이션은 DB 채택 후 R04가 별도 절차·순서를 명시한다.
6. R05가 입구 시험 후 S1 실제 생성·종료·최종 저장을 확인한다. 이후 보완/이관·조회/긴급·장애/복구·전체 회귀를 수행한다. 결과는 `runs/`와 개발 원장에 남긴다.

## 3 운영과 업데이트

- 상태 확인: compose 준비 후 `docker compose -f infra/compose.yaml ps`를 사용한다. 로그 열람은 권한 있는 역할이 수행하고 공유 전 비밀·개인정보를 가린다.
- 일시 중지/재시작: `docker compose -f infra/compose.yaml stop` / `start`를 사용한다. 중단된 processing 건은 외부 효과를 확인하며 자동으로 신규 처리권을 발급하지 않는다.
- 업데이트: 현재 이미지/설정/워크플로우·DB 버전을 기록 → 백업 확인 → 호환성/마이그레이션 검토 → 새 버전 배포 → VM 회귀 순서다. 이미지 교체만으로 데이터 롤백이 된다고 가정하지 않는다.
- 일반 재배포에 `down -v`·볼륨 삭제·DB 초기화를 사용하지 않는다. 이전 이미지와 호환되지 않는 스키마 변경은 별도 복구안을 먼저 작성한다.

## 4 백업과 복구

R01은 compose·배포 버전·환경 비밀/암호화 키의 안전한 복구 경로를, R04는 처리 상태·DLQ·서비스 DB 백업과 원자적 복원을, R03은 지식 원본·재색인·활성 버전 복구를 맡는다. 실제 주기·보존 기간·저장 위치·허용 중단/손실 시간은 D01/D03에서 VM 용량과 함께 정한다. Git은 비밀·DB 데이터·Jira 전체 데이터의 백업이 아니다.

복구 시 R01이 서비스를 통제하고 R04가 원 실행 종료·Jira 효과·미해결 DLQ·최신 처리권을 확인한다. R03이 필요 시 재색인하고 R05가 재시작/재처리·중복 없음·권한·S1을 검증한다. 암호화 키와 저장 데이터의 조합을 복원할 수 있는지 실제로 시험한 뒤 복구 가능으로 기록한다.
